## Current behavior in this branch

### Admission and history

- Every ordinary conversation, Job, and run requires a **real Bear-owned hat**, including on a Bear with zero hats. A conversation must have its canonical owner/hat binding; Work requires the exact live, uncancelled run and an eligible Job hat covering its assigned surfaces. A zero-hat Bear cannot execute through a legacy fallback.
- Browser and BearWire admission fail before ordinary message/turn persistence or Work checkout/provisioning when these bindings are absent or ineligible. Old unbound transcripts remain owner/admin-readable history, not writable ordinary sessions; NULL-owner history is admin-only. An admin's right to inspect another person's history does not grant execution as its owner.
- A pending IDE session does not create a durable `den-conv-*` conversation until hat admission succeeds. An explicitly configured IDE default may select a real hat; `/hat` lists or selects a Bear-owned hat before productive interaction. Reconnect retains the canonical binding. No default hat is fabricated, imported settings do not manufacture one, and no records or permissions are automatically promoted into one.
- Source admission precedes every production inference, including all continuations; client tool-result recording, compacted-output reads, and direct Den tools also recheck the live canonical actor, immutable source, hat, and exact Work run where applicable. Cached labels, a session ID, caller-supplied origin, or an admin-visible transcript cannot substitute for admission. Source checks do not imply every effect has complete hat-action/resource filtering.
- Conversations/transcripts, client sessions, Docket tasks/Jobs, and memory have distinct canonical owners. Model replay and human history are separate projections; human history excludes diagnostic/model-only records. Historical session-ID collisions and ownerless records remain quarantined, not inferred into ownership. Same-creator cross-conversation generic artifact isolation and remaining session-only joins still need audit.

### Identity, settings, and runtime context

- Bear-admin stance detail/configuration/provisioning is retired. `/bear/{slug}/models` owns named Bear model configurations, the Bear default, budget, loop control, and Bifrost key settings, not per-stance rows. Admin per-profile model and profile-registration routes are gone. Native initialization opens memory, ensures the runtime plan, and compiles managed configuration; it never creates or refreshes a stance/profile registry.
- Historical profile model/loop rows, contracts, settings, and audit encodings remain historical inspection data, not live overrides. Ordinary model selection uses explicit conversation pins, canonical hat configuration references, and Bear/deployment defaults, in that order. Runtime defaults, loop control, continuation, and compaction policy derive from verified execution origin and current governance, never a stale profile override.
- Managed compilation produces the bound Bear-wide base and platform-owned interaction modes only. Bound base parsing is independent of legacy role contracts and their metadata. No production inference selects a role prompt or role contract. Turn assembly selects the current hat identity from its canonical source and validates compiled source versions; it does not copy a historical stance contract into a hat. Hat names and explicitly authored short summaries are directory data, not permissions. Full identity belongs only to the selected hat; purpose remains admin-facing.
- The Rust types `TrustProfile` / `BearProfile` / `BearStance` and their aliases are removed; derived runtime-context metadata uses `RuntimeContextLabel`. Its five source-kind labels describe channel conversation, armature conversation, Job run, curation operation, and observation operation. Historical `chat/pair/work/curate/watch` encoding remains for schema/audit compatibility. A label cannot reconstruct authority or configure a stance; browser task sessions remain a distinct verified origin despite sharing the historical `pair` encoding.
- Effective capability ceilings come from verified `TurnExecutionOrigin` and governance. Channel conversations have no local armature tools; browser task controls do not invent an armature; disconnected or restricted-governance turns cannot borrow connected-client tools. Typed descriptor audiences and connected-armature filtering apply to native rosters and dispatch. The common hat-grant/resource resolver is still partial.

### Bear-scoped gateway availability and embedding authentication (2026-10-10)

**Current code/test follow-on; not deployed:** Den's selectable model table supplies product metadata and capability facts, not proof that a Bear can execute a model. Web/ACP choices now intersect that metadata with the Bear's authenticated Bifrost catalog. New configuration/default/hat/pin choices and existing-Bear legacy edits validate a fresh catalog before writes; no global, static, or cached positive result authorizes a new selection. Stored unavailable configurations remain inspectable and unchanged, and clearing references/pins remains possible for repair. New-Bear setup treats a submitted model as an unverified proposal: it provisions the new Bear's key, verifies the choice with that key, and only then saves the active default and continues initialization. Failed setup compensates only its own untouched new root; intervening work blocks cleanup and the response identifies the saved Bear rather than encouraging duplicate creation.

Canonical-source admission and primary-model preflight now precede native context assembly/optional recall and transcript writes. Browser sends and BearWire preflight also reject a known missing/unavailable model or missing/rejected key before turn-side effects. Execution distinguishes **an existing canonical explicit pin during a genuine catalog outage** from **a new selection**: continuity may attempt that same pin using credential-matched cached transport, or Responses when no cached transport is known. It never substitutes another model and never overrides a successful catalog denial, missing key or rejected key. Preview labels such a retained pin `unverified`, not available; fresh choices remain empty during the outage. Provider/catalog state can change after any check; this is preflight and recovery, not an availability lease or inference-success guarantee.

`ModelAvailabilityFailure` preserves structured reason through runtime/HTTP/BearWire boundaries. Public errors include a checked model reference, actionable recovery and the request reference, never provider bodies, credential values or endpoint URLs. Codes are `model_missing` / `model_unavailable` (HTTP 400), `virtual_key_missing` / `virtual_key_rejected` (409), and `catalog_unavailable` (503); key setup failures are not mislabeled as human login or membership failures. For the reported `openai/gpt-6-sol` case, the diagnostic states that the selected model is missing from this Bear's Bifrost catalog and directs the human to choose an available model in Models or repair Bifrost access.

Catalog requests disable redirects and mark the virtual-key header sensitive. A per-Bear refresh queue, persistent generations and canonical-credential rechecks prevent old positive responses or rejected/rotated credentials from repopulating usable cache authority. Legitimate concurrent checks still perform fresh authenticated requests and converge without inventing a catalog outage.

All Bear-scoped embedding searches and indexing now resolve the Bear's current server-side virtual key per operation and send `x-bf-vk`, with no global/admin key fallback. Missing/invalid credentials stop before HTTP. Optional recall still degrades rather than rejecting chat; indexing failures remain safely recorded. The key must authorize the configured embedding model as well as any primary models. Embedding transport/status failures discard provider bodies, inputs, credentials and URLs, and embedding redirects are disabled. No key enters model context or Bear memory through this path.

### Memory and publication

- Per-Bear SQLite owns canonical memory. Ordinary tools and turn-start projection use only own-source private notes, authorized selected-hat knowledge, and Bear-wide `core/`, with canonical scope/access checks. There is **no ordinary Legacy profile-memory path**, even on zero-hat Bears. Generic-readable old profile-local records remain restricted historical admin/review data with unverified ownership; protected history is excluded even from those generic admin reads. Paths, imported IDs, and session-like strings do not prove a source owner.
- Bound prompt-memory reads select Bear-wide and exact-client-session blocks; writes/patches are confined to the current session. Historical profile/work-surface blocks do not widen ordinary context. Opaque caller runtime text cannot replace Den's compiled supplement.
- Member library feed/search/browse/direct-ID/history expose only current authorized hat/core records, not raw notes. Semantic recall filters candidates, rechecks current SQLite scope/lifecycle/access, and reconstructs text there; stale vector payloads confer no access. Recall indexes only eligible current `core/` and hat records; source-local and profile-local records are **never indexed**, even with zero hats. Stale legacy derived-point cleanup is retried before embedding, without changing canonical historical SQLite. Profile-string recall APIs are removed. Recall can disclose reviewed text to the configured embedding provider and stores derived passages/vectors in Qdrant; network, privacy, and usage costs apply. Unavailable recall falls back to curated keyword search. Derived cleanup neither promotes historical records nor grants ordinary legacy-memory access.
- Owners can inspect their source's private conversation notes separately from the shared library; Bear-admin transcript inspection alone does not grant that owner-only view. Raw entity/reflection/proposal inspection remains admin-only until provenance is scoped, **not** a personal-body ownership override. The Phase 4 follow-on below makes generic record/admin/tool/proposal/graph/indexing reads exclude all ACL history and permanent personal-publication classification; these are no longer unscoped reads of protected canonical bodies. Physical-integrity counts/high-water remain base-storage operations intentionally.
- Source→hat and hat→`core/` publication require verified provenance and newly authored shareable content, with explicit audience acknowledgement and optimistic current-head checks. The source stays private/unchanged. Explicit legacy review may cite an eligible **generic-readable** historical record as unknown-owner provenance; it cannot re-author a classified source or overwrite/invalidate a classified target head. It does not import history as ordinary memory, assign ownership, or automatically promote it. The model-facing legacy core-update tool and autonomous legacy core-action proposals are retired.
- Automatic hat sharing starts off. When enabled, Curate can rewrite a verified conversation-local note into knowledge for every authorized wearer, including eligible Jobs. Source, creator membership, hat, proposal, and opt-in are checked before synthesis and again at publication. Invalid/provider-failed synthesis stays private/pending; typed synthesis failures have durable delayed retries and bounded recovery, with recurring model-call cost. Curation is tool-free and does not certify privacy or turn content into trusted instruction. Live Bifrost synthesis/background delivery remain unvalidated.
- Old Pair Plans and shared work-surface scaffold **model tools** are retired. Historical rows/records are not live planning or shared-memory write authority. Current task/Docket state remains separate from memory.

### Portable identity reconnection (Phase 6A)

**2026-10-21, reconnection code/storage/HTTP tests verified; live acceptance and broader gates pending, not deployed:** **Backup & move → Imported identities** at `/bear/{slug}/portability/identities` lets a current verified Bear Admin review reconnection to a current verified Bear member, or revoke an existing mapping. It is a human management boundary, not a model API or an ordinary personal-memory inspection screen. It displays identity metadata and receipts, never memory content. Matching names, numeric IDs, bundle possession, and imported receipts do not authorize a mapping.

- Export records source-qualified account labels/IDs, host, source Bear, and exporter association in SQLite `user_identity_origins` before taking the snapshot. It does not allocate a person for the exporter. Import quarantines every source binding; Alice and Bob retain distinct portable person IDs and unchanged memory audiences until separately authorized destination mappings exist. Source availability, credentials, and transcripts are not needed.
- Preparation and a separate confirmation use actor/session/Bear-bound expiring nonces and a server-held typed identity/binding snapshot. Confirmation rechecks current eligibility while holding Postgres User/email/Bear locks through an atomic SQLite mapping/entity/handle/generation/receipt commit. Source-metadata snapshot comparison, including selected/displaced origins and `display_name`, occurs inside that SQLite transaction. Generic entity/handle mutation, merge, and split remain prohibited for active or quarantined user identities.
- Exactly one person is active per Bear/account. With a separate replacement acknowledgement, either a fresh or populated destination identity can be parked with **all** records, relations, candidate bodies, and provenance preserved; Pending personal candidates become Quarantined. It is not merged, discarded, or automatically jointly recalled with the selected person. The parked person remains reconnectable through another review.
- Revocation followed by a separately reviewed reconnection corrects a mistaken mapping. Authority generations reject stale contexts even if the same Bear/account/person tuple is restored. Memory records, their lifecycle, IDs, and audience targets are never rewritten; only local attachment/resolution metadata changes. Receipt history provides management recovery after a lost confirmation response, prioritizing local decisions over future-dated source receipts and handling malformed imported history defensively. Optional history-load failures no longer block the mapping UI; imported historical metadata never grants current authority.

At the initial Phase 6A checkpoint, the additive SQLite tables were `user_identity_generations`, `user_identity_origins`, and `user_identity_receipts`, alongside existing identity classification. That slice needed no Postgres migration or dependency change and initially retained **version 3**. This is historical: current Phase 4 exports now use **v4** for compatibility with the required personal-record guards. The existing full private admin snapshot remains distinct from unimplemented scoped sharing and pre-export curation flushing.

### Server-only personal candidates (Phase 3 foundation)

**2026-10-21, storage/provenance foundation delivered; not deployed or end-user enabled:** `den-memory::personal_candidates` and `den-service::personal_memory` accept only **preferred name + explicit user request + durable intention**. Names are trimmed then validated at 1–128 UTF-8 bytes, with controls rejected before trimming; `PreferredName` has redacted `Debug` and neither it nor `PersonalCandidate` implements serde. No model tool, personal-body UI, HTTP or runtime route is registered. Phase 3's end-user/model-request exit is still open; Phase 4 now has the narrow server-only owner-decision backend below, not ordinary personal recall.

- Candidate bodies stay in dedicated `personal_memory_candidates`, never generic proposals/observations. Only separate explicit Phase 4 approval creates a permanently classified canonical `memory_records` body; generic inspection/curation is not an authorized personal-body destination. Owner-bound get/list/withdraw require a fresh exact Bear/person/user/generation binding; provenance IDs confer no grants.
- Capture defaults **false**, with explicit trusted human-settings operations and no human UI yet. Consent is authority-epoch-bound. Explicit human `capture=false` now atomically withdraws unpublished Pending/Quarantined candidates **and retracts the current preferred name**, intentionally changing the earlier candidate-only toggle. Reenabling revives neither. Staging deduplicates by Bear/person/conversation + exact note UUID + exact trimmed value after current capture/source checks; different users or sources stay separate. `CandidateState::Published` is derived from the immutable publication decision while the raw `pending` row and old CHECK constraint remain unchanged. Same-source/name dedup **can return the existing Published candidate**, including after retraction, but creates no new Pending candidate and never reactivates the fact. Published candidates are excluded from pending review, withdrawal and quarantine, **not** idempotent dedup.
- The service checks current membership, owned active canonical conversation and a real same-Bear hat, holding Postgres authority/source locks through SQLite writes in a cancellation-safe spawned task. Hat-sharing opt-in is irrelevant to this private lane. SQLite checks exact canonical conversation/note columns, current visible active lifecycle and **absence of all access-rule history**. It neither reads/copies the source body nor reclassifies the source.
- Private import rebases only owning `bear_id`s, preserves person/candidate/fact IDs and immutable source Bear/user/generation/conversation/note provenance, quarantines unpublished Pending and resets capture disabled. Local identity parking quarantines unpublished Pending too. Unlike explicit human opt-out, import/parking do not retract published facts. ### Server-only preferred-name owner decisions (narrow Phase 4)

**2026-10-21, narrow code/test and SQLx checkpoint verified; not deployed.** [Phase 4](../roadmap/USER_ASSOCIATED_BEAR_MEMORY_PLAN.md#phase-4--curation-and-lifecycle) implements explicit owner-approved preferred-name publication, correction and retraction, not autonomous Curate or ordinary automatic recall.

- **Owner and source authority:** the service caller must use the trusted authenticated user and current Bear membership/current binding; Bear Admin has no ownership override. New approval requires current capture consent, current candidate generation and the original owned active canonical conversation/real same-Bear hat, plus exact current SQLite source eligibility. User/Bear/membership and new-decision source conversation/hat locks stay held through SQLite completion in a cancellation-safe spawned task. They are authority fences, not a distributed write transaction. Current-head reads, retraction and immutable receipt replay require current membership/binding, but not capture consent or the original source conversation/account online. Source IDs/provenance are never grants.
- **Canonical minimal fact:** the entire `memory_records.content_text` is just the validated trimmed name, not a sentence/prompt/instruction/transcript. Metadata is `{}` and `logical_path` remains its **NULL default**; neither carries PII. The record, mandatory descriptive subject, mandatory owner audience, immutable publication decision/provenance, sequence allocation and any prior-version invalidation/access-rule supersession commit atomically. Source memory stays unchanged.
- **Permanent protection and versioning:** `personal_memory_publications` classifies every version permanently, even after ACL withdrawal or physical ACL loss. Correction CAS uses the latest publication's exact head version, including retracted/suppressed heads. Retraction appends a separate immutable `personal_memory_retractions` tombstone while invalidating the body/withdrawing active rules, retaining the head version. Current reads return Active/Retracted/Suppressed and only an eligible active head carries a value. A repeated publication returns its original receipt, **not** proof of activity; retry, reenabling or reconnection never resurrects a retracted/superseded fact.

Authorized reconnection restores only the same person's same still-active fact even with capture false. Explicit human capture false instead retracts the current preferred name and withdraws pending candidates atomically; fresh consent plus a new eligible candidate/approval is needed for a new fact.

## Enabling Work is not starting a run

Work starts off for a hat and needs permitted surfaces plus explicit identity-audience acknowledgement. A populated hat also requires admin review of its **entire historical memory**, including archived/superseded versions, in paginated views with full-snapshot count/fingerprint and identity fingerprint checks. If any historical record has ACL history or permanent personal-publication classification, review fails closed: admin status cannot disclose it, and silently filtering it would approve an incomplete history. Den fences the canonical snapshot, rechecks both fingerprints, and records a review receipt before enabling Work. Later eligible runs can read subsequent curated hat knowledge; enablement is not a per-run empty-memory test. Revoking Work or surfaces denies subsequent admission/effects. Neither enablement nor a hat grant supplies a Job, credential, tool, workspace, or network route.

## Hat access policy: partial effect cutover

Den owns Bear/hat-scoped action and normalized destination grants. Current supported intersections are:

- **Den web:** fetch/search check the live owner/member/source/hat, supported action and destination grants, and Bear blocks. Fetch can use an exact single-call/continuation URL approval; HTTPS-host persistence is an admin-only current-hat choice. Search requires the supported provider and host grant. DNS/private-IP checks, pinning, no redirects, and no ambient proxy apply.
- **Editor filesystem reads:** supported read-only descriptors can use an exact-root Den-owned grant after current owner/hat/root checks and a second check before effect. Admin ACP persistence is atomically tied to the winning obligation. Work, writes, commands, and MCP do not inherit it. Symlink checks are not race-free open-by-handle enforcement.
- **Work sandbox egress:** eligible runs receive the hat/surface host intersection; upgraded relays consult Den before each new external connection using the exact live run/token and provisioned ceiling. Revocation triggers cancellation/token revocation and retried teardown. Existing connections can last up to 60 seconds; this is not per-HTTP-request or instantaneous revocation. The optional provider's real Job/revocation flow remains unverified.

There is **no ordinary Legacy network or Cargo fallback**. Retained old approvals/helper behavior cannot admit an unbound ordinary source. The unrestricted Cargo helper is denied for hat-bound Work, and automatic Cargo preparation is denied during hat-bound Rust provisioning; those Jobs need a separately grant-enforced dependency cache.

This is **not a complete `HatGrantResolver`**: Den action/resource filtering remains partial across web, filesystem reads, and sandbox egress. Capability catalogs, broader Den effects (including Cabinet), provider upstream/git/credentials, and other client-tool families still need the common resolver. Supported ACP persistent choices do not generalize to other tools. Broader Den effects and other bounded `Always for [hat]` choices are next; [Gate 0A](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md#gate-0a--hat-owned-tool-and-network-permissions-partial-cutover-exit-pending) owns that work.

Instructions come through repository Markdown, not an ordinary stance registry or invented default hat. Generic system-origin starts, dispatch, results, and continuations are denied. Observation is a narrow worker/intake source, not a generic ordinary model session.
