## Current behavior in this branch

- Per-Bear SQLite is the canonical memory store. Legacy `profile_local` notes and shared `core/` remain intact. Den Postgres holds Bear-owned hat definitions and optional conversation/Job hat bindings. A hat only restricts the Bear's existing surface grants. The Work-hat resolver denies access after eligibility or a surface grant is revoked.
- A *bound* conversation or eligible Work run gets a Den-verified source/hat scope. Bound Pair `memory_write_entry` writes source-local notes. Model-facing direct read, browse, and keyword search admit only own-source, bound-hat, and shared records, subject to access-bearing rules; a known logical path does not grant access. Bound turn-start context likewise excludes legacy profile highlights and rechecks derived recall hits against SQLite. Reviewed hat heads are eligible for derived semantic indexing with a typed hat ID in Qdrant; source-local raw notes and access-bearing records remain unindexed. If recall is configured, embedding sends reviewed hat/core text through Bifrost to its configured embedding provider and Qdrant holds derived passage text and vectors; this has the provider's privacy, network, and usage-cost implications. When a Bear gains its first hat, the admin route enqueues a best-effort recall reconcile: configured Bears no longer embed legacy profile-local notes, and a successful reconcile removes their previously indexed points. No-hat Bears retain legacy profile recall until that transition; derived cleanup can lag if recall is unavailable. Reviewed source→hat, legacy→hat, and hat→core writes best-effort enqueue a whole-Bear recall reconcile when enabled. Bound turn recall rechecks the canonical source/hat/core grant and rebuilds its text from SQLite, not a stale vector payload.
- Bound runtime prompt-block selection and model-facing prompt-block tools expose Bear-wide blocks and exact-client-session blocks, not profile-local or work-surface blocks. Bound prompt-block writes and patches are limited to that client session; Postgres refuses block-ID reassignment across Bears or scopes. `memory_status` and `session_info` report the narrower bound scope instead of profile counts/labels. Bound turn assembly discards opaque supplied runtime-context text and rebuilds its Den-owned supplement.
- The Bear memory library now distinguishes ordinary members from Bear-admin inspection. Members' dashboard, recent feed, keyword search, browse, direct record lookup, and history read only current, visible shared or Bear-owned hat records, with a canonical SQLite scope check and fail-closed access-bearing checks. History is constrained to the selected record's scope and hat. When Qdrant and embeddings are available, member semantic search filters candidate IDs to Bear-core and the Bear's owned hats, then rechecks current, visible SQLite records and rebuilds every displayed snippet and label there. It falls back to curated keyword search if recall is unavailable or no current authorized hits remain; raw source/profile records and stale or access-bearing passages cannot become member-visible from Qdrant. Member feed, search, browse, and detail pages label entries “Bear-wide” or by the Bear-owned hat name from stored SQLite scope columns and Postgres hats, rather than inferring a label from a logical path; their links no longer print technical paths. Admin inspection retains its path-oriented view. Separately, the owner of a hat-bound browser conversation may inspect up to 50 of that source's current private notes in its chat view; this owner-only view is not the shared memory library and does not expose hat/core records, another source's raw notes, or restricted records. Bear-admin transcript inspection alone does not grant this private-notes view. The memory dashboard also shows up to eight current, unrestricted private-note previews from the signed-in human's 200 most recently updated active, hat-bound conversations, separately from the curated library and without direct raw-record links. Canonical Postgres ownership and membership are checked before bounded SQLite source selection; even Bear admins see only their own notes in this panel. Valid browser conversation IDs link back to the chat, while other sources remain unlinked; older conversations outside the window are still accessible through their own source views where supported. Member library feed, search, browse and direct-ID routes remain curated-only. Entity, reflection/evidence, and proposal detail pages are Bear-admin-only because their raw provenance is not scoped yet. Admin inspection deliberately retains broad access, including legacy and source-local notes; its contents should not be treated as generally shared Bear memory.
- Human conversation reads now use the canonical Postgres `created_by_user_id`: ordinary Bear members can read/continue only their own conversations, while Bear admins may inspect even legacy ownerless records. Browser chat list/history/artifacts/model/title/archive/delete/send and BearWire conversation/session/run entry points enforce this boundary. Browser `default` is per-user while preserving the historical owner's legacy default; a first `new-*` message creates a durable owner-scoped conversation and announces its ID. Human-visible history excludes hidden/admin/diagnostic-only tool records; model replay remains a distinct projection. Bear management activity, reflection, context/prompt-memory previews, stance internals, and advanced diagnostics are now admin-only; member overview omits Bear-wide raw counts/titles. Legacy compaction events cannot be joined safely across Bears by external ID and are no longer displayed in these management pages.
- Human Work surfaces now respect Docket job visibility: owner or Bear admin, or a member explicitly allowed by a `BearVisible` job. Job/run UI, BearWire Docket RPCs, and Den-hosted job/task tools deny other members' `SameUser` jobs by known ID as well as in listings. Work checkout and execution-attempt RPCs require the job creator/admin or an exact run-minted bearer token for a member of a `BearVisible` job. Docket task checkout, model-facing task-list sync, current-task selection and focused task activation recheck the job and session owner before attachment, private projection or execution. BearWire event and focused-transition pagination use Bear, user, and session columns before limiting; session open/close/run preflight rejects an already-used ID belonging to another user or Bear.
- Bear admins now have a Hats page to create and rename responsibilities, edit purposes and a separate hat identity, select a subset of already Bear-assigned work surfaces, review private source-local notes for promotion into a hat, and explicitly designate **one IDE default hat per Bear**. The ordinary Bear identity page lists hat names and short summaries without exposing their admin-only purpose text or internal stance list; technical stance diagnostics remain admin-only. Existing hat identities were initialized from their purposes; editing a Work-enabled hat's identity requires explicit acknowledgement of its Work audience. The preview renders the same repository-owned hat-identity component used by bound model turns, escaped for HTML. On managed Bears, an admin-only collapsed panel also shows the effective older chat/pair/Work instruction sources, distinguishing Bear customizations from published defaults, for manual identity review; none is copied into a hat automatically. Bear-wide steering and platform-owned interaction-mode instructions are composed separately; the hat's authored text does not grant authority. For a Bear without a designated default, a new IDE conversation starts unbound; `/hat` can bind it before the first turn, but later turns do not silently acquire a hat. They can start a new owner-scoped chat wearing a hat, bind an existing empty, inactive conversation once, or bind an eligible draft Job once. Job use starts off; it requires a permitted surface. An empty hat can enable Work after a Work-audience acknowledgement of its identity; a populated hat also requires a Bear-admin review of its **entire historical hat-memory snapshot**. Den checks the reviewed memory count/fingerprint and identity fingerprint again under a SQLite writer fence and the Postgres hat lock, then records an audit receipt with both hashes in Postgres before enabling Work. The review shows 100 records per page while streaming a full-history fingerprint from canonical SQLite without loading the entire hat into a page response. Both fingerprints travel across pages; a changed identity or any historical record—including an in-place metadata edit—requires starting again at page one. The final-page acknowledgement attests that the admin inspected every page. Review covers the entire hat history; an inconsistent or incomplete snapshot fails closed. Disabling Work or removing surfaces immediately revokes eligibility. Hats do not grant tools, credentials, or armature trust, and ordinary members cannot change them.
- For hat-bound `chat`/`pair` conversations and eligible Job-bound `work` runs, Den now selects identity from the canonical hat binding, not the stance name or caller text. The repository-owned base identity fragment explains the hat metaphor and the selected hat, lists only Bear-owned hat names and explicitly authored short summaries (up to 160 characters each), and gives the selected hat's full identity text. A Bear-admin editor requires acknowledging that a summary is visible to conversations and authorized Work wearing **any** hat; existing hats have no summary until an admin authors one. Longer purposes are never auto-copied into the directory or injected into another hat's prompt. The source Bear and selected hat are rechecked; catalog text does not grant authority or permit a mid-session hat switch. The managed compiled config provides the Bear-wide baseline/steering and repository-owned interaction-mode fragments; new turns re-read the hat's current authored identity, so edits take effect on the next turn without copying a stance contract or another hat's text. The compiled prompt source version is checked before reusing bound components. A configured Bear with no verified binding fails before model-turn assembly rather than silently falling back to another identity. No-hat Bears and internal `curate`/`watch` roles keep their legacy per-stance prompt path pending a separate internal-role decision. Existing per-stance identity contracts remain stored for compatibility but are not selected for bound interactive or Work turns.
- The effective capability table is keyed by verified `TurnExecutionOrigin` and governance. It still differentiates channel conversation, browser task session, armature conversation, authorized Job run, curator, and observer; hat prose cannot grant capabilities. BearWire `run.start` resolves the canonical live Work-run or conversation binding before constructing `TurnAuthority` for local tool advertisement, routing, and its permission envelope. A disconnected armature, noninteractive governance, or channel-origin Write label does not grant client-local filesystem, terminal, or forwarded MCP tools. Browser task controls retain session-task access without local armature tools. Native turn construction now threads the verified origin into model tool merging, selects Den descriptor audiences from that typed origin (including separate channel, browser-task, armature, Work, curation, and observation audiences), and derives its compatibility profile for prompt and budget selection. Serialized `allowed_roles` is a derived display-only projection; deserialized client descriptors cannot grant an executable Den audience. Chat no longer removes Den tool definitions on turns merely because the prompt lacks tool-related words; configured work/cabinet/task ceilings still narrow the stable origin-eligible roster. Client-result continuations retain the native session's verified `TurnExecutionOrigin` and derived compatibility profile rather than adopting a caller-supplied Pair label; Den server-tool policy is compiled from that retained origin and denies a profile mismatch before invocation. The approved Den-tool continuation also compiles policy from that retained origin and requires its exact live Work-run ID—not merely a Work profile or a session ID—to match the original source. The direct runtime invoker requires the effective policy to match the retained origin, the context profile to match its derived compatibility profile, and the builtin Den tool descriptor to admit that origin, and a Work-run ID to be present only for a Work origin. For ordinary channel, browser-task, and armature calls, the direct invoker rechecks the acting human's current Bear membership before each Den-hosted tool effect, including workflow and Cabinet tools that bypass the core dispatcher. For Work-origin calls, it rechecks the exact live, uncancelled session-bound run and its current Job hat/surface eligibility before each Den-hosted tool effect; the registered profile binding remains a separate legacy check. This is a per-tool check, not a per-sandbox-network-connection revocation barrier. Turn-start memory projection selects a live Work run by canonical session binding before using its source, and denies a Pair/Chat turn that tries to use the same Work session ID as a conversation. The core Den-tool dispatcher still resolves a registered profile from `bear_profile_bindings` and applies the descriptor's profile-compatibility projection; internal-role memory paths also use profile labels. These are remaining authority inputs, so stances cannot yet be removed from runtime registration. The [active plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) requires a verified-origin tool-execution denial matrix before that cutover. The member-visible Tools catalog describes typical channel/editor/Job/internal availability instead of stance names; actual grants still depend on the current verified turn and connected client.
- For new BearWire/ACP editor sessions, Den now allocates one durable owner-scoped conversation before the first turn and binds the IDE default if configured. The Bear-level code token still authenticates the human and armature; it does not select a hat or grant tools. The armature advertises `/hat`: bare `/hat` lists Bear-owned hats without using the selection opportunity, while `/hat <name or UUID>` can override the default only as the first productive ACP interaction. Den independently checks the canonical owner, Bear, client session, hat, and absence of prior messages and turns. Reopening a session retains its conversation's hat. Headless Work uses the assigned Job's hat rather than treating the IDE default as Job authority.
- A Bear admin may explicitly enable **automatic memory sharing** for a hat; it starts off and applies to all authorized uses of that hat, including eligible Job runs. Enabling or disabling Job use does not silently change this choice. Bound Pair can then request `propose_hat` using the UUID `entry_id` of its own current source-local note. Den verifies the conversation owner, Bear/hat binding, note scope and lifecycle, stores a typed source/hat link in SQLite columns rather than model JSON/paths, and enqueues `memory_curate`. The worker makes one tool-free Curate inference through the Bear's configured Bifrost key, passing the private note and proposal summary to its embedding-independent LLM provider; this has privacy, network, and usage-cost implications. A closed decision can retain locally or propose newly authored shareable text. Before a publish, Den rechecks current canonical source/proposal, the original conversation creator's current Bear membership, and the hat's sharing opt-in under the Postgres hat/conversation/membership locks; SQLite writes the hat entry, provenance, and proposal decision atomically; Den best-effort enqueues derived recall when configured. Neither the Pair proposal nor Curate model output selects the hat, Work audience, or tools. Verbatim private-note copying is denied, but an LLM's content judgment cannot *guarantee* privacy or prompt-injection resistance; the opt-in warns admins that other members and authorized Job runs wearing the hat may consume curated text with their own approved tools. Missing keys, invalid model output, or provider failures leave the private candidate pending, without a routine human queue. Only typed synthesis-unavailable outcomes enter durable delayed recovery: after one minute, ten minutes, one hour, and six hours, each retry chain settles into a once-daily cadence. The completed run and its queued successor commit together, and the worker cannot claim a future run early. Unsuccessful candidates remain private and pending; disabled-sharing and authorization denials do not retry. Separately enqueued runs for the same proposal can create additional calls; this is not a global per-proposal rate limit. Recurring provider calls can incur ongoing network, privacy, and usage cost while an opted-in hat remains eligible. A bounded background sweep also inspects completed synthesis-failure runs without queued successors (up to 100 run/proposal pairs per sweep, advancing its window daily). It rechecks that the original SQLite proposal is still pending with a canonical verified source, that the conversation still belongs to the hat, and that the hat currently opts in. It enqueues at most one recovery chain for each exhausted run/proposal, due no sooner than the next day; it does not immediately transmit old private notes to the model on deployment. Legacy path-only proposals and resolved/unauthorized candidates are not recovered. Stale sources and departed creators are rejected before model synthesis, and membership is checked again at publication. Legacy paths/JSON remain unverified, Work-run notes cannot use this conversation-source lane, and the separate explicit hat→core publication path remains in place. Fake-Curate tests cover the publication/denial matrix; a live Bifrost synthesis and background-worker round trip have not been exercised.
- Bear-admin hat review takes a verifiable source-local conversation or Work-run note and requires newly authored shareable content, a written rationale, and explicit acknowledgement of the Bear-member audience (plus Work when enabled). The original source stays private. The canonical SQLite transaction writes the hat record and its source→target promotion together; a replacement needs the reviewed current head's ID and cannot silently overwrite a changed entry. Hidden, archived, superseded, access-bearing, orphaned, and ambiguous legacy profile notes cannot enter this route. Reviewed content remains **data**, never a prompt instruction or permission grant.
- Admins can inspect a paginated inventory of legacy `profile_local` records by stored profile and eligibility. These notes retain **unverified ownership**, even if an imported ID contains a branch, commit, path, or client-session-like string. A separate admin-only route permits a current visible legacy record (including a non-UUID imported ID) to be cited as provenance for **newly authored** hat content after an explicit unknown-owner/all-member acknowledgement and, if Work is enabled, a Work-audience acknowledgement. The original remains profile-local and inaccessible to other ordinary sessions; hidden, archived, superseded, and access-bearing records are excluded. This is manual reauthoring, not automatic scope assignment or a claim of conversation ownership.
- A Bear admin can now inspect a current, visible hat entry and publish **newly authored** Bear-wide `core/` text after explicitly acknowledging all-member and future Work audiences. The per-Bear SQLite transaction rechecks the exact hat/source columns, access rules, current head and expected core head; it writes the new core record and hat→core promotion together. The hat source remains unchanged. Archived, hidden, access-bearing, other-hat, and raw source-local records cannot enter this route. The legacy model-facing `memory_apply_core_update` tool is retired and no longer advertised or executable, even for Bears without hats. Autonomous curate never applies legacy `promote_to_core`/`summarize_into_core` proposals: it resolves pending ones as rejected with a retirement reason, without publishing or creating a human-review queue. New `memory_request_review` calls cannot suggest those actions. Existing shared records are not deleted. The opted-in Curate lane publishes only into the source conversation's bound hat, which may also be worn by authorized Job runs. It does not publish into `core/`. This remains a deliberate admin route for Bear-wide publication, not an automatic proposal→core write.
- Ordinary members can now choose a Bear-owned hat before starting a new browser conversation. Den creates and binds the owned canonical conversation before its first turn; the chat list shows its hat, and another member cannot access that source's raw history. Job creation similarly requires a Work-enabled hat whenever the Bear has configured hats; Docket validates that the hat permits all assigned surfaces and stores the hat atomically with the Job and its initial run. Invalid or revoked selections cannot leave a silently unbound Job. Bears without hats still permit the explicit legacy unbound path.
- **Legacy turn cutover:** Once a Bear has any hats, an unbound human conversation or Job Work run can no longer start an ordinary turn or resolve legacy profile memory. Browser and BearWire reject before persisting the user message or turn; BearWire Work checkout rejects an unbound or ineligible Job before binding a session or minting an execution attempt, the automatic dispatcher skips ineligible Jobs before enqueueing, and the dispatch worker fails any already-queued ineligible run before starting a task, minting an armature token, or provisioning a sandbox. An ACP session without an IDE default must choose a hat with `/hat <name or UUID>` before its first turn. The browser still lists owner-accessible historical unbound threads as read-only and preserves owner/admin transcript inspection; it no longer advertises a synthetic writable “Main chat” on a configured Bear. Bears with no hats retain the legacy unbound path. Opted-in Curate can publish into a Job-capable hat; large-hat Work review includes the entire historical record set. Historical profile-local records still have no assigned source owners even if a reviewer cited them in a new hat entry, and shared/core content has not been retroactively reviewed. Legacy ownerless conversations are admin-only even when associated with an older Work run; they are not silently claimed by a session ID. Some model-facing task/entry/run list paths still use post-limit filtering and can underfill pages. The new Postgres client-session ownership guard serializes inserts and rejects any new ID reused by another user or Bear, including concurrent claims; it deliberately leaves historical duplicates intact and quarantined. A dev-database inventory found 2 legacy collision groups (41 rows) and 40 ownerless conversations; 30 ownerless rows had only a client-session association and no independently identified message author, so their ownership cannot safely be auto-assigned. Remaining internal session-only event joins and an explicit owner-review path still need a canonical identity audit before claiming complete Bear-wide isolation. Current tool authorization still uses registered profile/descriptor roles. Legacy persistent web host approvals remain Bear-scoped only for no-hat Bears. Creating a hat atomically revokes the Bear's active legacy approvals, and new Bear-wide approval writes are refused once hats exist; the migration revokes older active approvals on configured Bears without reassigning them to a default hat. They do not authorize Den-hosted `web_fetch` in a configured-hat conversation; newly provisioned hat-bound Work sandboxes now receive only the intersection of their hat's exact HTTPS hosts and the assigned work surface's saved host ceiling; no-hat Work retains the surface-only legacy path, and the armature consults Den's authenticated hat directory before any local-tool remembered approval: configured or unverifiable sessions are one-time-only and that Bear/client cache is cleared; only verified no-hat sessions retain legacy remembered scopes. URL-targeted client approvals are one-time-only on all Bears. A one-time Den-hosted `web_fetch` approval is bound to its originating native tool call and continuation request, consumed atomically for the matching URL, and cannot be reused for another call, session, Bear, or redirect; historical one-hour ACP URL approvals without hat provenance are revoked by migration. Den fetches do not follow redirects or inherit ambient HTTP proxies and pin connections to DNS addresses vetted as public before the request; this can prevent access in deployments that relied on a proxy. This closes the one-time leak for Den-hosted web fetch. Den Postgres also stores canonical Bear/hat-scoped tool and HTTPS-host grant records with descriptor-key normalization, admin-only writes, explicit future-Job-audience acknowledgement, idempotency, revocation, and an owner-verified conversation read that requires both a tool grant and an exact HTTPS-host grant for a potential fetch. The Bear-admin Hats page can add and revoke `web_fetch`, `web_search`, and exact HTTPS-host grants independently; it displays the current Den-owned state, rejects IPs, patterns and custom ports, and explains that a granted hat fetch can skip later native Pair prompts, while Job egress is narrowed only at sandbox provisioning. The Bear resources page hides Bear-wide approvals and `allowed` source edits when hats exist; preferred sources remain search-ranking hints and explicit blocks still apply. The Work dispatcher now resolves the eligible run's canonical hat and assigned surface before starting a task or minting a token, computes that intersection from Den Postgres, and passes a typed run ceiling to the provider. Den first requires a healthy provider advertising support for run ceilings; an old or unreachable provider is rejected before task start or token mint. The upgraded provider intersects again with its current managed root; a run ceiling on an open-network sandbox is rejected. `Some([])` means no external host relays and `None` preserves no-hat compatibility. Den records the hat-run host ceiling when provisioning, then rechecks each owned running/reporting run's current Job/hat/surface policy on worker polls. If the prior host ceiling is no longer authorized, or a pre-cutover run has no snapshot, Den requests cancellation, revokes the run token, and retries provider teardown until acknowledged. This is **not an instantaneous per-connection gateway check**: an existing relay can remain reachable until the next poll and successful teardown, especially during provider outages. Credential injection and provider-side upstream/git operations remain separate, and a granted host alone never authorizes a Job. Den-hosted `web_fetch` now checks the current conversation owner and membership, both the tool and exact HTTPS-host grants, and the Bear's explicit block policy at its fetch decision for a configured-hat conversation. It ignores legacy Bear-wide allows and host approvals; a matching one-time URL/continuation still permits one eligible fetch, and a revoked hat grant takes effect on the next decision. The fetch audit distinguishes `hat_host` from `approved_once` (the new audit migration also admits the previously missing `approved_once` kind). For a Den-verified native Pair call, a current tool and exact-host grant can now route `web_fetch` directly to Den without another ACP pause; absent grants still request one exact one-time approval. Bear-admin ACP prompts for a valid HTTPS URL can also offer `Always for [current hat]: HTTPS host` with the future-conversation/eligible-Job audience shown. BearWire resolves the canonical conversation, owner/admin membership, and exact URL from the persisted obligation, atomically adds the tool and host grants only for the winning permission result, and denies the continuation if the post-claim grant cannot be persisted. A late, duplicate, non-admin, wrong-hat, Work-bound, or invalid-destination choice cannot create a grant. The original native approval is consumed even if the newly created hat grant also permits the fetch, so revocation cannot resurrect that old obligation. Client-local tools and other network actions do not inherit this ACP choice. `web_search` sends the full query to the configured external provider. A bound conversation can use the Brave provider only when its current creator is still a Bear member and its hat has both the `web_search` action grant and the exact `api.search.brave.com` host grant. Revoking either or explicitly blocking that host in the Bear web policy denies the next search. Den validates and pins the provider's DNS addresses, follows no redirects, and does not inherit an ambient HTTP proxy. The configured server-side Brave key is independent of the hat grant; query disclosure and provider usage can incur privacy and cost. An unsupported or unconfigured provider cannot be used by a configured hat; no-hat Bears retain legacy search authorization (with the hardened Brave transport). Other Den tools, provider-side Job network paths, descriptor advertisement, armature-local persistent tool grants, and individual connections through already-provisioned sandbox relays still do not consult this grant table; local hatted tool actions require a fresh interactive decision instead of borrowing an old cache entry. Native Pair model-tool merging now omits `web_search` for a bound hat without both grants, a configured Brave provider, or an unblocked destination; untrusted client descriptors cannot reintroduce it. A grant or block change affects the next model roster, and execution independently rechecks the live policy. Other capability catalogs and tool advertisements are not yet driven by one shared resolver.

## Enabling Work is not starting a run

The *historical memory review* applies **when a Bear admin changes a hat from Work off to Work on**, not each time a sandboxed Work run starts. Work eligibility (the bound Job, Work-enabled hat, and current surfaces) is separately rechecked at checkout/provisioning and turn start. An empty hat can pass without a historical review. For a populated hat, Den shows the identity and all historical records—including archived and superseded versions—and requires the admin to record a rationale acknowledging that eligible Job runs become readers. The transition fails closed if the identity or memory changed after the first page was loaded or if the bounded snapshot could not include every record; each page checks both fingerprints and a successful decision stores an audit receipt. This prevents previously interactive-only knowledge from silently gaining a new audience.

Once Work is enabled, a subsequently authorized Job-bound run may read the hat's curated memory **even if entries were added after enablement**, as well as its own run-local notes and Bear-wide `core/`. Opted-in Curate may continue to add rewritten facts for that same hat; eligible Job runs are already part of its disclosed audience. Neither enabling the hat nor assigning it a surface starts a run or grants a credential, tool, egress right, or permission: the Job, current surface grants, and execution policy must still authorize each run. The sandbox bounds the work environment; it does not hide data already given to the model from the run's approved actions. This gate addresses silent sharing of *hat* memory, not the separate question of whether existing `core/` content is appropriate for Work.

## Target to validate

One Bear can wear a named, user-configured **hat** for a responsibility and limited resources/actions. A hat is reusable across conversations and approved Work Jobs, but never grants credentials, tools, or authorization on its own. The intended ordinary memory read set is:

1. Its own uncurated notes, keyed by the canonical conversation, Work run, or stable intake unit—not a transient client connection. Transcript history remains separate from memory.
2. Reviewed knowledge for its bound hat.
3. Bear-wide curated `core/` knowledge.

No ordinary run reads another source's uncurated notes, even under the same hat or legacy profile. Curation has an auditable cross-source review path and may retain a note locally, promote reviewed material to a hat, or deliberately promote it to Bear-wide `core/`. Promoted content is data, never an instruction or an authorization grant.

**Hat publication policy:** a hat has one curated-memory audience: Bear members and authorized runs wearing it, including future Job runs when Work is enabled. With the Bear-admin's hat-learning opt-in, Curate may rewrite a verified private source note as a new, concise fact for that hat, or retain it privately. The curator cannot choose a different hat, permission, or audience; uncertain, sensitive, or instruction-like material remains local. The original note is never copied into the shared library. Source and hat authority are rechecked at publication; curated content remains untrusted data, not an instruction or safety certificate. An existing populated hat needs a historical memory/identity review when Job use is first enabled; subsequent curated facts do not require individual approval or a separate Work-specific memory tier. Every run still needs its own authorized Job and enforced tools, approvals, credentials, and egress. Bear-wide `core/` publication is a distinct, explicit choice, not an automatic consequence of hat learning.

**Hat-owned access policy (target; partial Den web-fetch cutover):** Den will own the positive tool/action and network-destination grants under the canonical Bear-owned `hat_id`, usable by authorized conversations and Job runs wearing that hat. A hat grant never grants the human Bear membership, a connected armature, a workspace root, a credential, or a Job. Effective access is the intersection of its hat grant with current actor/connection rights, tool descriptor and platform denials, the work surface's resource and network bounds, the Job/run scope, and approval obligations. Changing hats cannot carry an approval across hats; revocation takes effect at advertisement, call execution, and outbound egress. Internal curation and observation use separate Den-owned execution authority rather than borrowing a hat.

An interactive request should offer **“Just this time”** for that exact action and target (one run/tool obligation, no remembered grant) and, when the approver can manage the hat's shared policy, **“Always for [hat name]”** with the applicable narrower directory, workspace, command, host, or account shown in the label. Persistent grants include future authorized Job runs wearing that hat; the prompt must say so. A member without hat-policy authority may ask its manager for the persistent grant but cannot make a Bear-wide policy change by approving a local action. “Always” never overrides an independent bound or makes a client-local tool available after disconnect. See the [active hats plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) and [ACP permission UX target](../architecture/acp-tool-call-permission-ux-spec.md).

Stance names may eventually be derived labels rather than authority inputs if typed source, hat, verified armature, Job, and governance policy preserves all denial invariants. A focused typed-policy regression now confirms that Chat, Pair, and Work still have different grants under identical armature/governance inputs. `chat`, `pair`, `curate`, `work`, and `watch` therefore remain current implementation vocabulary; [the plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) requires a replacement resolver and end-to-end denial suite before changing this axis.

## Questions before user-facing rollout

- Current member-library policy shares each Bear-owned hat's reviewed memory with every Bear member. Is a person-private hat needed before user-facing setup? Do not promote a person's raw note to this shared audience silently.
- How should member semantic search recheck candidate IDs against canonical SQLite and reconstruct safe snippets before being enabled? What reviewed owner/participant policy should resolve legacy NULL-owner conversations and quarantined session-ID collisions without treating a client-session association as proof of ownership?
- Which historical profile-local records have a verifiable source ID, and how will ambiguous records remain reviewable without automatic promotion?
- How does changing a hat's resources or Work eligibility invalidate active run authority and trigger review of already-curated memory?
