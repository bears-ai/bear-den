# Bear memory and hats

**Owner:** Den memory, runtime-policy, and Bear management code owners.
**Scope:** Bear memory visibility, hats, session/Job binding, and curation.
**Current as of:** 2026-09-30; evidence: `services/den/crates/den-memory/src/schema.sql`, `services/den/crates/den-memory/src/scoped.rs`, `services/den/crates/den-memory/src/library/mod.rs`, `services/den/crates/den-service/src/bears/hats/memory_binding.rs`, `services/den/crates/den-service/src/bears/hats/identity.rs`, `services/den/crates/den-service/src/bears/hats/work_review/tests.rs`, `services/den/crates/den-runtime/src/agent_loop/identity_tests.rs`, `services/den/crates/den-service/src/prompt_memory_block_store.rs`, `services/den/crates/den-runtime/src/agent_loop/assembler.rs`, `services/den/crates/den-web/src/bear/memory.rs`, `services/den/crates/den-web/src/bear/memory/tests.rs`, and `services/den/src/core/tools/tests/prompt_memory_bound.rs`. These are branch-code claims, not proof of a public release. On 2026-09-30 a local Den image build and single-service recreate passed `/health` and `BEARS_LIVE_MODEL_SMOKE=0 ./scripts/smoke.sh` (2 passed, optional live-model test skipped); hat identity and review semantics are covered by the linked focused tests, not by that smoke suite.
**Target:** [Hats and session memory boundaries plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) (user-facing hat setup, reviewed promotion, and migration remain open).

The target changes some of their memory contracts; this topic does not supersede those ADRs.

## Current behavior in this branch

- Per-Bear SQLite is the canonical memory store. Legacy `profile_local` notes and shared `core/` remain intact. Den Postgres holds Bear-owned hat definitions and optional conversation/Job hat bindings. A hat only restricts the Bear's existing surface grants. The Work-hat resolver denies access after eligibility or a surface grant is revoked.
- A *bound* conversation or eligible Work run gets a Den-verified source/hat scope. Bound Pair `memory_write_entry` writes source-local notes. Model-facing direct read, browse, and keyword search admit only own-source, bound-hat, and shared records, subject to access-bearing rules; a known logical path does not grant access. Bound turn-start context likewise excludes legacy profile highlights and rechecks derived recall hits against SQLite. New source/hat records are **not yet indexed** for semantic recall; member semantic search remains keyword-only until candidates can be canonically rechecked.
- Bound runtime prompt-block selection and model-facing prompt-block tools expose Bear-wide blocks and exact-client-session blocks, not profile-local or work-surface blocks. Bound prompt-block writes and patches are limited to that client session; Postgres refuses block-ID reassignment across Bears or scopes. `memory_status` and `session_info` report the narrower bound scope instead of profile counts/labels. Bound turn assembly discards opaque supplied runtime-context text and rebuilds its Den-owned supplement.
- The Bear memory library now distinguishes ordinary members from Bear-admin inspection. Members' dashboard, recent feed, keyword search, browse, direct record lookup, and history read only current, visible shared or Bear-owned hat records, with a canonical SQLite scope check and fail-closed access-bearing checks. History is constrained to the selected record's scope and hat. Member semantic search is disabled: requesting it uses curated keyword search, never broad Qdrant passage text. Separately, the owner of a hat-bound browser conversation may inspect up to 50 of that source's current private notes in its chat view; this owner-only view is not the shared memory library and does not expose hat/core records, another source's raw notes, or restricted records. Bear-admin transcript inspection alone does not grant this private-notes view. Entity, reflection/evidence, and proposal detail pages are Bear-admin-only because their raw provenance is not scoped yet. Admin inspection deliberately retains broad access, including legacy and source-local notes; its contents should not be treated as generally shared Bear memory.
- Human conversation reads now use the canonical Postgres `created_by_user_id`: ordinary Bear members can read/continue only their own conversations, while Bear admins may inspect even legacy ownerless records. Browser chat list/history/artifacts/model/title/archive/delete/send and BearWire conversation/session/run entry points enforce this boundary. Browser `default` is per-user while preserving the historical owner's legacy default; a first `new-*` message creates a durable owner-scoped conversation and announces its ID. Human-visible history excludes hidden/admin/diagnostic-only tool records; model replay remains a distinct projection. Bear management activity, reflection, context/prompt-memory previews, stance internals, and advanced diagnostics are now admin-only; member overview omits Bear-wide raw counts/titles. Legacy compaction events cannot be joined safely across Bears by external ID and are no longer displayed in these management pages.
- Human Work surfaces now respect Docket job visibility: owner or Bear admin, or a member explicitly allowed by a `BearVisible` job. Job/run UI, BearWire Docket RPCs, and Den-hosted job/task tools deny other members' `SameUser` jobs by known ID as well as in listings. Work checkout and execution-attempt RPCs require the job creator/admin or an exact run-minted bearer token for a member of a `BearVisible` job. Docket task checkout, model-facing task-list sync, current-task selection and focused task activation recheck the job and session owner before attachment, private projection or execution. BearWire event and focused-transition pagination use Bear, user, and session columns before limiting; session open/close/run preflight rejects an already-used ID belonging to another user or Bear.
- Bear admins now have a Hats page to create and rename responsibilities, edit purposes and a separate hat identity, select a subset of already Bear-assigned work surfaces, review private source-local notes for promotion into a hat, and explicitly designate **one IDE default hat per Bear**. Existing hat identities were initialized from their purposes; editing a Work-enabled hat's identity requires explicit acknowledgement of its Work audience. The identity-prompt cutover resets preexisting Work-enabled hats to Work off, immediately making their existing Jobs ineligible for new Work checkout/dispatch until an admin reviews identity and memory and re-enables the hat. Previous memory-only review receipts are retained as history, not accepted as identity reviews; rollback does not silently restore Work grants. The preview renders the same repository-owned hat-identity component used by bound model turns, escaped for HTML. Bear-wide steering and platform-owned interaction-mode instructions are composed separately; the hat's authored text does not grant authority. For a Bear without a designated default, a new IDE conversation starts unbound; `/hat` can bind it before the first turn, but later turns do not silently acquire a hat. They can start a new owner-scoped chat wearing a hat, bind an existing empty, inactive conversation once, or bind an eligible draft Job once. Autonomous Work starts off; it requires a permitted surface. An empty hat can enable Work after a Work-audience acknowledgement of its identity; a populated hat also requires a Bear-admin review of its **entire historical hat-memory snapshot**. Den checks the reviewed memory count/fingerprint and identity fingerprint again under a SQLite writer fence and the Postgres hat lock, then records an audit receipt with both hashes in Postgres before enabling Work. The review shows 100 records per page, carrying both fingerprints across pages; a changed identity or memory snapshot requires starting again at page one. The final-page acknowledgement attests that the admin inspected every page. Hats above the bounded 500-record snapshot limit remain blocked, not silently approved from a truncated view. Disabling Work or removing surfaces immediately revokes eligibility. Hats do not grant tools, credentials, or armature trust, and ordinary members cannot change them.
- For hat-bound `chat`/`pair` conversations and eligible Job-bound `work` runs, Den now selects identity from the canonical hat binding, not the stance name or caller text. The managed compiled config provides the Bear-wide baseline/steering and repository-owned interaction-mode fragments; new turns re-read the hat's current authored identity, so edits take effect on the next turn without copying a stance contract or another hat's text. The compiled prompt source version is checked before reusing bound components. A configured Bear with no verified binding fails before model-turn assembly rather than silently falling back to another identity. No-hat Bears and internal `curate`/`watch` roles keep their legacy per-stance prompt path pending a separate internal-role decision. Existing per-stance identity contracts remain stored for compatibility but are not selected for bound interactive or Work turns.
- For new BearWire/ACP editor sessions, Den now allocates one durable owner-scoped conversation before the first turn and binds the IDE default if configured. The Bear-level code token still authenticates the human and armature; it does not select a hat or grant tools. The armature advertises `/hat`: bare `/hat` lists Bear-owned hats without using the selection opportunity, while `/hat <name or UUID>` can override the default only as the first productive ACP interaction. Den independently checks the canonical owner, Bear, client session, hat, and absence of prior messages and turns. Reopening a session retains its conversation's hat. Headless Work uses the assigned Job's hat rather than treating the IDE default as Job authority.
- Bear-admin hat review takes a verifiable source-local conversation or Work-run note and requires newly authored shareable content, a written rationale, and explicit acknowledgement of the Bear-member audience (plus Work when enabled). The original source stays private. The canonical SQLite transaction writes the hat record and its source→target promotion together; a replacement needs the reviewed current head's ID and cannot silently overwrite a changed entry. Hidden, archived, superseded, access-bearing, orphaned, and ambiguous legacy profile notes cannot enter this route. Reviewed content remains **data**, never a prompt instruction or permission grant.
- Ordinary members can now choose a Bear-owned hat before starting a new browser conversation. Den creates and binds the owned canonical conversation before its first turn; the chat list shows its hat, and another member cannot access that source's raw history. Job creation similarly requires a Work-enabled hat whenever the Bear has configured hats; Docket validates that the hat permits all assigned surfaces and stores the hat atomically with the Job and its initial run. Invalid or revoked selections cannot leave a silently unbound Job. Bears without hats still permit the explicit legacy unbound path.
- **Legacy turn cutover:** Once a Bear has any hats, an unbound human conversation or Job Work run can no longer start an ordinary turn or resolve legacy profile memory. Browser and BearWire reject before persisting the user message or turn; BearWire Work checkout rejects an unbound or ineligible Job before binding a session or minting an execution attempt, the automatic dispatcher skips ineligible Jobs before enqueueing, and the dispatch worker fails any already-queued ineligible run before starting a task, minting an armature token, or provisioning a sandbox. An ACP session without an IDE default must choose a hat with `/hat <name or UUID>` before its first turn. The browser still lists owner-accessible historical unbound threads as read-only and preserves owner/admin transcript inspection; it no longer advertises a synthetic writable “Main chat” on a configured Bear. Bears with no hats retain the legacy unbound path. Routine `curate`-owned promotion and full review beyond the 500-record limit remain open. Historical profile-local records have not been assigned source owners, and shared/core content has not been retroactively reviewed. Legacy ownerless conversations are admin-only even when associated with an older Work run; they are not silently claimed by a session ID. Some model-facing task/entry/run list paths still use post-limit filtering and can underfill pages. The new Postgres client-session ownership guard serializes inserts and rejects any new ID reused by another user or Bear, including concurrent claims; it deliberately leaves historical duplicates intact and quarantined. A dev-database inventory found 2 legacy collision groups (41 rows) and 40 ownerless conversations; 30 ownerless rows had only a client-session association and no independently identified message author, so their ownership cannot safely be auto-assigned. Remaining internal session-only event joins and an explicit owner-review path still need a canonical identity audit before claiming complete Bear-wide isolation. See the [memory model](../architecture/memory-model.md) and [state-machine inventory](../architecture/den-state-machine-inventory.md).

## Enabling Work is not starting a run

The *historical memory review* applies **when a Bear admin changes a hat from Work off to Work on**, not each time a sandboxed Work run starts. Work eligibility (the bound Job, Work-enabled hat, and current surfaces) is separately rechecked at checkout/provisioning and turn start. An empty hat can pass without a historical review. For a populated hat, Den shows the identity and all historical records—including archived and superseded versions—and requires the admin to record a rationale acknowledging that autonomous Work becomes a reader. The transition fails closed if the identity or memory changed after the first page was loaded or if the bounded snapshot could not include every record; each page checks both fingerprints and a successful decision stores an audit receipt. This prevents previously interactive-only knowledge from silently gaining a new audience.

Once Work is enabled, a subsequently authorized Job-bound run may read the hat's curated memory **even if entries were added after enablement**, as well as its own run-local notes and Bear-wide `core/`. Future curation into that hat must therefore consider Work as an audience. Neither enabling the hat nor assigning it a surface starts a run or grants a credential, tool, egress right, or permission: the Job, current surface grants, and execution policy must still authorize each run. The sandbox bounds the work environment; it does not hide data already given to the model from the run's approved actions. This gate addresses silent sharing of *hat* memory, not the separate question of whether existing `core/` content is appropriate for Work.

## Target to validate

One Bear can wear a named, user-configured **hat** for a responsibility and limited resources/actions. A hat is reusable across conversations and approved Work Jobs, but never grants credentials, tools, or authorization on its own. The intended ordinary memory read set is:

1. Its own uncurated notes, keyed by the canonical conversation, Work run, or stable intake unit—not a transient client connection. Transcript history remains separate from memory.
2. Reviewed knowledge for its bound hat.
3. Bear-wide curated `core/` knowledge.

No ordinary run reads another source's uncurated notes, even under the same hat or legacy profile. Curation has an auditable cross-source review path and may retain a note locally, promote reviewed material to a hat, or deliberately promote it to Bear-wide `core/`. Promoted content is data, never an instruction or an authorization grant.

**Simple hat promotion rule:** a hat's reviewed memory is available to all its permitted uses, including an authorized Work run when the hat has Work enabled. The curator must consider that audience when promoting new entries; enabling Work on a populated hat requires reviewing existing entries first. This is a hat-configuration transition, not a per-run empty-memory requirement. Each run still needs its own authorized Job and bounded tools/egress. No extra per-record visibility tier is proposed.

Stance names may eventually be derived labels rather than authority inputs if typed source, hat, verified armature, Job, and governance policy preserves all denial invariants. Until tested, `chat`, `pair`, `curate`, `work`, and `watch` remain current implementation vocabulary; [the plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) requires an end-to-end slice before changing this axis.

## Questions before user-facing rollout

- Current member-library policy shares each Bear-owned hat's reviewed memory with every Bear member. Is a person-private hat needed before user-facing setup? Do not promote a person's raw note to this shared audience silently.
- How should member semantic search recheck candidate IDs against canonical SQLite and reconstruct safe snippets before being enabled? What reviewed owner/participant policy should resolve legacy NULL-owner conversations and quarantined session-ID collisions without treating a client-session association as proof of ownership?
- Which historical profile-local records have a verifiable source ID, and how will ambiguous records remain reviewable without automatic promotion?
- How does changing a hat's resources or Work eligibility invalidate active run authority and trigger review of already-curated memory?
