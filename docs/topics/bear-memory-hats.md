# Bear memory and hats

**Owner:** Den memory, runtime-policy, and Bear management code owners.
**Scope:** Bear memory visibility, hats, session/Job binding, and curation.
**Current as of:** 2026-09-30; evidence: `services/den/crates/den-memory/src/schema.sql`, `services/den/crates/den-memory/src/scoped.rs`, `services/den/crates/den-memory/src/library/mod.rs`, `services/den/crates/den-service/src/bears/hats/memory_binding.rs`, `services/den/crates/den-service/src/bears/hats/identity.rs`, `services/den/crates/den-service/src/bears/hats/work_review/tests.rs`, `services/den/crates/den-runtime/src/agent_loop/identity_tests.rs`, `services/den/crates/den-service/src/prompt_memory_block_store.rs`, `services/den/crates/den-runtime/src/agent_loop/assembler.rs`, `services/den/crates/den-web/src/bear/memory.rs`, `services/den/crates/den-web/src/bear/memory/tests.rs`, and `services/den/src/core/tools/tests/prompt_memory_bound.rs`. These are branch-code claims, not proof of a public release. On 2026-09-30 the current local Den image was built and `bears-den` alone recreated; `/health` and `BEARS_LIVE_MODEL_SMOKE=0 ./scripts/smoke.sh` passed (2 passed, optional live-model test skipped). Hat curation, legacy review, semantic authorization, and identity behavior are covered by focused tests. The opt-in `den-service` test `real_qdrant_reconciles_first_hat_and_rechecks_member_hits` passed against live Qdrant with synthetic deterministic 8D vectors: it verified first-hat legacy point cleanup, hat-filtered member search, canonical SQLite reconstruction of poisoned passage text, and rejection of a stale archived hit. Its isolated collection was removed. This test makes no Bifrost or external embedding call; neither it nor the default smoke suite validates live embedding quality or the running Den worker.
**Target:** [Hats and session memory boundaries plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) (user-facing hat setup, reviewed promotion, and migration remain open).
**Decisions:** [SQLite-first canonical Bear memory](../decisions/adr-0031-sqlite-first-canonical-store-for-bear-agent-memory-and-tasks.md), [Trust profiles and governance](../decisions/adr-0039-trust-profiles-and-governance.md). The target changes some of their memory contracts; this topic does not supersede those ADRs.

## Current behavior in this branch

- Per-Bear SQLite is the canonical memory store. Legacy `profile_local` notes and shared `core/` remain intact. Den Postgres holds Bear-owned hat definitions and optional conversation/Job hat bindings. A hat only restricts the Bear's existing surface grants. The Work-hat resolver denies access after eligibility or a surface grant is revoked.
- A *bound* conversation or eligible Work run gets a Den-verified source/hat scope. Bound Pair `memory_write_entry` writes source-local notes. Model-facing direct read, browse, and keyword search admit only own-source, bound-hat, and shared records, subject to access-bearing rules; a known logical path does not grant access. Bound turn-start context likewise excludes legacy profile highlights and rechecks derived recall hits against SQLite. Reviewed hat heads are eligible for derived semantic indexing with a typed hat ID in Qdrant; source-local raw notes and access-bearing records remain unindexed. If recall is configured, embedding sends reviewed hat/core text through Bifrost to its configured embedding provider and Qdrant holds derived passage text and vectors; this has the provider's privacy, network, and usage-cost implications. When a Bear gains its first hat, the admin route enqueues a best-effort recall reconcile: configured Bears no longer embed legacy profile-local notes, and a successful reconcile removes their previously indexed points. No-hat Bears retain legacy profile recall until that transition; derived cleanup can lag if recall is unavailable. Reviewed source→hat, legacy→hat, and hat→core writes best-effort enqueue a whole-Bear recall reconcile when enabled. Bound turn recall rechecks the canonical source/hat/core grant and rebuilds its text from SQLite, not a stale vector payload.
- Bound runtime prompt-block selection and model-facing prompt-block tools expose Bear-wide blocks and exact-client-session blocks, not profile-local or work-surface blocks. Bound prompt-block writes and patches are limited to that client session; Postgres refuses block-ID reassignment across Bears or scopes. `memory_status` and `session_info` report the narrower bound scope instead of profile counts/labels. Bound turn assembly discards opaque supplied runtime-context text and rebuilds its Den-owned supplement.
- The Bear memory library now distinguishes ordinary members from Bear-admin inspection. Members' dashboard, recent feed, keyword search, browse, direct record lookup, and history read only current, visible shared or Bear-owned hat records, with a canonical SQLite scope check and fail-closed access-bearing checks. History is constrained to the selected record's scope and hat. When Qdrant and embeddings are available, member semantic search filters candidate IDs to Bear-core and the Bear's owned hats, then rechecks current, visible SQLite records and rebuilds every displayed snippet and label there. It falls back to curated keyword search if recall is unavailable or no current authorized hits remain; raw source/profile records and stale or access-bearing passages cannot become member-visible from Qdrant. Member feed, search, browse, and detail pages label entries “Bear-wide” or by the Bear-owned hat name from stored SQLite scope columns and Postgres hats, rather than inferring a label from a logical path; their links no longer print technical paths. Admin inspection retains its path-oriented view. Separately, the owner of a hat-bound browser conversation may inspect up to 50 of that source's current private notes in its chat view; this owner-only view is not the shared memory library and does not expose hat/core records, another source's raw notes, or restricted records. Bear-admin transcript inspection alone does not grant this private-notes view. Entity, reflection/evidence, and proposal detail pages are Bear-admin-only because their raw provenance is not scoped yet. Admin inspection deliberately retains broad access, including legacy and source-local notes; its contents should not be treated as generally shared Bear memory.
- Human conversation reads now use the canonical Postgres `created_by_user_id`: ordinary Bear members can read/continue only their own conversations, while Bear admins may inspect even legacy ownerless records. Browser chat list/history/artifacts/model/title/archive/delete/send and BearWire conversation/session/run entry points enforce this boundary. Browser `default` is per-user while preserving the historical owner's legacy default; a first `new-*` message creates a durable owner-scoped conversation and announces its ID. Human-visible history excludes hidden/admin/diagnostic-only tool records; model replay remains a distinct projection. Bear management activity, reflection, context/prompt-memory previews, stance internals, and advanced diagnostics are now admin-only; member overview omits Bear-wide raw counts/titles. Legacy compaction events cannot be joined safely across Bears by external ID and are no longer displayed in these management pages.
- Human Work surfaces now respect Docket job visibility: owner or Bear admin, or a member explicitly allowed by a `BearVisible` job. Job/run UI, BearWire Docket RPCs, and Den-hosted job/task tools deny other members' `SameUser` jobs by known ID as well as in listings. Work checkout and execution-attempt RPCs require the job creator/admin or an exact run-minted bearer token for a member of a `BearVisible` job. Docket task checkout, model-facing task-list sync, current-task selection and focused task activation recheck the job and session owner before attachment, private projection or execution. BearWire event and focused-transition pagination use Bear, user, and session columns before limiting; session open/close/run preflight rejects an already-used ID belonging to another user or Bear.
- Bear admins now have a Hats page to create and rename responsibilities, edit purposes and a separate hat identity, select a subset of already Bear-assigned work surfaces, review private source-local notes for promotion into a hat, and explicitly designate **one IDE default hat per Bear**. Existing hat identities were initialized from their purposes; editing a Work-enabled hat's identity requires explicit acknowledgement of its Work audience. The identity-prompt cutover resets preexisting Work-enabled hats to Work off, immediately making their existing Jobs ineligible for new Work checkout/dispatch until an admin reviews identity and memory and re-enables the hat. Previous memory-only review receipts are retained as history, not accepted as identity reviews; rollback does not silently restore Work grants. The preview renders the same repository-owned hat-identity component used by bound model turns, escaped for HTML. On managed Bears, an admin-only collapsed panel also shows the effective older chat/pair/Work instruction sources, distinguishing Bear customizations from published defaults, for manual identity review; none is copied into a hat automatically. Bear-wide steering and platform-owned interaction-mode instructions are composed separately; the hat's authored text does not grant authority. For a Bear without a designated default, a new IDE conversation starts unbound; `/hat` can bind it before the first turn, but later turns do not silently acquire a hat. They can start a new owner-scoped chat wearing a hat, bind an existing empty, inactive conversation once, or bind an eligible draft Job once. Autonomous Work starts off; it requires a permitted surface. An empty hat can enable Work after a Work-audience acknowledgement of its identity; a populated hat also requires a Bear-admin review of its **entire historical hat-memory snapshot**. Den checks the reviewed memory count/fingerprint and identity fingerprint again under a SQLite writer fence and the Postgres hat lock, then records an audit receipt with both hashes in Postgres before enabling Work. The review shows 100 records per page while streaming a full-history fingerprint from canonical SQLite without loading the entire hat into a page response. Both fingerprints travel across pages; a changed identity or any historical record—including an in-place metadata edit—requires starting again at page one. The final-page acknowledgement attests that the admin inspected every page. Hats with more than 500 historical records can now be reviewed; an inconsistent/incomplete snapshot still fails closed. Disabling Work or removing surfaces immediately revokes eligibility. Hats do not grant tools, credentials, or armature trust, and ordinary members cannot change them.
- For hat-bound `chat`/`pair` conversations and eligible Job-bound `work` runs, Den now selects identity from the canonical hat binding, not the stance name or caller text. The repository-owned base identity fragment explains the hat metaphor and the selected hat, lists only Bear-owned hat names and explicitly authored short summaries (up to 160 characters each), and gives the selected hat's full identity text. A Bear-admin editor requires acknowledging that a summary is visible to conversations and authorized Work wearing **any** hat; existing hats have no summary until an admin authors one. Longer purposes are never auto-copied into the directory or injected into another hat's prompt. The source Bear and selected hat are rechecked; catalog text does not grant authority or permit a mid-session hat switch. The managed compiled config provides the Bear-wide baseline/steering and repository-owned interaction-mode fragments; new turns re-read the hat's current authored identity, so edits take effect on the next turn without copying a stance contract or another hat's text. The compiled prompt source version is checked before reusing bound components. A configured Bear with no verified binding fails before model-turn assembly rather than silently falling back to another identity. No-hat Bears and internal `curate`/`watch` roles keep their legacy per-stance prompt path pending a separate internal-role decision. Existing per-stance identity contracts remain stored for compatibility but are not selected for bound interactive or Work turns.
- Moving identity to hats did **not** retire stances. `EffectivePolicy` still grants different capability sets for `chat`, `pair`, and `work` with the same governance and armature availability: `chat` lacks armature-local tools/session-task authority, `pair` may have them through a verified client, and `work` executes an authorized Job without acquiring general conversation authority. Hat prose is not an input to these grants. A comparison-only `TurnExecutionOrigin` now derives existing policy defaults from typed channel, browser-task-session, armature, Work, curator, or intake origin; it is used by authenticated browser task controls, BearWire session and focused Docket task controls, and the web-chat Den-tool edge without changing grants. Browser task controls intentionally keep Pair-equivalent session-task access but no armature tools, while web-chat model tools remain Chat-scoped. Native tool merging and `TurnAuthority` now require the effective `UseArmatureTools` capability before accepting armature-local descriptors: even a Write session-mode label cannot grant a local read/edit/terminal tool to `chat`, `curate`, or `watch`. BearWire's forwarded MCP descriptors and fallback filesystem read are subject to the same armature-capability gate; Pair retains its stable client/MCP surface across ordinary turns. The rest of runtime/tool routing still uses `TrustProfile`; no stance can be retired until the full route-level denial matrix and canonical origin derivation are proven.
- For new BearWire/ACP editor sessions, Den now allocates one durable owner-scoped conversation before the first turn and binds the IDE default if configured. The Bear-level code token still authenticates the human and armature; it does not select a hat or grant tools. The armature advertises `/hat`: bare `/hat` lists Bear-owned hats without using the selection opportunity, while `/hat <name or UUID>` can override the default only as the first productive ACP interaction. Den independently checks the canonical owner, Bear, client session, hat, and absence of prior messages and turns. Reopening a session retains its conversation's hat. Headless Work uses the assigned Job's hat rather than treating the IDE default as Job authority.
- A Bear admin may explicitly enable **autonomous learning** for a Work-off hat; it starts off and enabling Work resets it to off. Bound Pair can then request `propose_hat` using the UUID `entry_id` of its own current source-local note. Den verifies the conversation owner, Bear/hat binding, note scope and lifecycle, stores a typed source/hat link in SQLite columns rather than model JSON/paths, and enqueues `memory_curate`. The worker makes one tool-free Curate inference through the Bear's configured Bifrost key, passing the private note and proposal summary to its embedding-independent LLM provider; this has privacy, network, and usage-cost implications. A closed decision can retain locally or propose newly authored shareable text. Before a publish, Den rechecks current canonical source/proposal, the explicit opt-in, and Work-off audience under the Postgres hat/conversation locks; SQLite writes the hat entry, provenance, and proposal decision atomically; Den best-effort enqueues derived recall when configured. Neither the Pair proposal nor Curate model output selects the hat, Work audience, or tools. Verbatim private-note copying is denied, but an LLM's content judgment cannot *guarantee* privacy or prompt-injection resistance; the one-time opt-in warns admins that other members' Pair sessions may consume curated text with approved tools. Missing keys, invalid model output, or provider failures leave the private candidate pending, without a routine human queue. Only typed synthesis-unavailable outcomes receive two durable delayed retries (after one minute and ten minutes): the completed run and its queued successor commit together, and the worker cannot claim a future run early. After three total attempts the proposal remains private and pending; Work-on, disabled-hat, and authorization denials do not retry. Resuming a candidate after the retry budget is exhausted remains open. Stale sources are rejected. Legacy paths/JSON remain unverified, Work-on hats and Work-run notes cannot use this lane, and the separate admin-reviewed hat→core path remains in place. Fake-Curate tests cover the publication/denial matrix; a live Bifrost synthesis and background-worker round trip have not been exercised.
- Bear-admin hat review takes a verifiable source-local conversation or Work-run note and requires newly authored shareable content, a written rationale, and explicit acknowledgement of the Bear-member audience (plus Work when enabled). The original source stays private. The canonical SQLite transaction writes the hat record and its source→target promotion together; a replacement needs the reviewed current head's ID and cannot silently overwrite a changed entry. Hidden, archived, superseded, access-bearing, orphaned, and ambiguous legacy profile notes cannot enter this route. Reviewed content remains **data**, never a prompt instruction or permission grant.
- Admins can inspect a paginated inventory of legacy `profile_local` records by stored profile and eligibility. These notes retain **unverified ownership**, even if an imported ID contains a branch, commit, path, or client-session-like string. A separate admin-only route permits a current visible legacy record (including a non-UUID imported ID) to be cited as provenance for **newly authored** hat content after an explicit unknown-owner/all-member acknowledgement and, if Work is enabled, a Work-audience acknowledgement. The original remains profile-local and inaccessible to other ordinary sessions; hidden, archived, superseded, and access-bearing records are excluded. This is manual reauthoring, not automatic scope assignment or a claim of conversation ownership.
- A Bear admin can now inspect a current, visible hat entry and publish **newly authored** Bear-wide `core/` text after explicitly acknowledging all-member and future Work audiences. The per-Bear SQLite transaction rechecks the exact hat/source columns, access rules, current head and expected core head; it writes the new core record and hat→core promotion together. The hat source remains unchanged. Archived, hidden, access-bearing, other-hat, and raw source-local records cannot enter this route. The legacy model-facing `memory_apply_core_update` tool is retired and no longer advertised or executable, even for Bears without hats. Autonomous curate never applies legacy `promote_to_core`/`summarize_into_core` proposals: it resolves pending ones as rejected with a retirement reason, without publishing or creating a human-review queue. New `memory_request_review` calls cannot suggest those actions. Existing shared records are not deleted. The separate Work-off opt-in Curate lane can publish to a hat; Work-on and hat→core autonomous publication are not enabled by that lane. This remains a deliberate admin route for Bear-wide publication, not an automatic proposal→core write.
- Ordinary members can now choose a Bear-owned hat before starting a new browser conversation. Den creates and binds the owned canonical conversation before its first turn; the chat list shows its hat, and another member cannot access that source's raw history. Job creation similarly requires a Work-enabled hat whenever the Bear has configured hats; Docket validates that the hat permits all assigned surfaces and stores the hat atomically with the Job and its initial run. Invalid or revoked selections cannot leave a silently unbound Job. Bears without hats still permit the explicit legacy unbound path.
- **Legacy turn cutover:** Once a Bear has any hats, an unbound human conversation or Job Work run can no longer start an ordinary turn or resolve legacy profile memory. Browser and BearWire reject before persisting the user message or turn; BearWire Work checkout rejects an unbound or ineligible Job before binding a session or minting an execution attempt, the automatic dispatcher skips ineligible Jobs before enqueueing, and the dispatch worker fails any already-queued ineligible run before starting a task, minting an armature token, or provisioning a sandbox. An ACP session without an IDE default must choose a hat with `/hat <name or UUID>` before its first turn. The browser still lists owner-accessible historical unbound threads as read-only and preserves owner/admin transcript inspection; it no longer advertises a synthetic writable “Main chat” on a configured Bear. Bears with no hats retain the legacy unbound path. Autonomous promotion into Work-on hats remains disabled; large-hat Work review no longer has the previous 500-record cutoff. Historical profile-local records still have no assigned source owners even if a reviewer cited them in a new hat entry, and shared/core content has not been retroactively reviewed. Legacy ownerless conversations are admin-only even when associated with an older Work run; they are not silently claimed by a session ID. Some model-facing task/entry/run list paths still use post-limit filtering and can underfill pages. The new Postgres client-session ownership guard serializes inserts and rejects any new ID reused by another user or Bear, including concurrent claims; it deliberately leaves historical duplicates intact and quarantined. A dev-database inventory found 2 legacy collision groups (41 rows) and 40 ownerless conversations; 30 ownerless rows had only a client-session association and no independently identified message author, so their ownership cannot safely be auto-assigned. Remaining internal session-only event joins and an explicit owner-review path still need a canonical identity audit before claiming complete Bear-wide isolation. See the [memory model](../architecture/memory-model.md) and [state-machine inventory](../architecture/den-state-machine-inventory.md).

## Enabling Work is not starting a run

The *historical memory review* applies **when a Bear admin changes a hat from Work off to Work on**, not each time a sandboxed Work run starts. Work eligibility (the bound Job, Work-enabled hat, and current surfaces) is separately rechecked at checkout/provisioning and turn start. An empty hat can pass without a historical review. For a populated hat, Den shows the identity and all historical records—including archived and superseded versions—and requires the admin to record a rationale acknowledging that autonomous Work becomes a reader. The transition fails closed if the identity or memory changed after the first page was loaded or if the bounded snapshot could not include every record; each page checks both fingerprints and a successful decision stores an audit receipt. This prevents previously interactive-only knowledge from silently gaining a new audience.

Once Work is enabled, a subsequently authorized Job-bound run may read the hat's curated memory **even if entries were added after enablement**, as well as its own run-local notes and Bear-wide `core/`. Future curation into that hat must therefore consider Work as an audience. Neither enabling the hat nor assigning it a surface starts a run or grants a credential, tool, egress right, or permission: the Job, current surface grants, and execution policy must still authorize each run. The sandbox bounds the work environment; it does not hide data already given to the model from the run's approved actions. This gate addresses silent sharing of *hat* memory, not the separate question of whether existing `core/` content is appropriate for Work.

## Target to validate

One Bear can wear a named, user-configured **hat** for a responsibility and limited resources/actions. A hat is reusable across conversations and approved Work Jobs, but never grants credentials, tools, or authorization on its own. The intended ordinary memory read set is:

1. Its own uncurated notes, keyed by the canonical conversation, Work run, or stable intake unit—not a transient client connection. Transcript history remains separate from memory.
2. Reviewed knowledge for its bound hat.
3. Bear-wide curated `core/` knowledge.

No ordinary run reads another source's uncurated notes, even under the same hat or legacy profile. Curation has an auditable cross-source review path and may retain a note locally, promote reviewed material to a hat, or deliberately promote it to Bear-wide `core/`. Promoted content is data, never an instruction or an authorization grant.

**Simple hat promotion rule:** a hat's reviewed memory is available to all its permitted uses, including an authorized Work run when the hat has Work enabled. The curator must consider that audience when promoting new entries; enabling Work on a populated hat requires reviewing existing entries first. This is a hat-configuration transition, not a per-run empty-memory requirement. Each run still needs its own authorized Job and bounded tools/egress. No extra per-record visibility tier is proposed.

Stance names may eventually be derived labels rather than authority inputs if typed source, hat, verified armature, Job, and governance policy preserves all denial invariants. A focused typed-policy regression now confirms that Chat, Pair, and Work still have different grants under identical armature/governance inputs. `chat`, `pair`, `curate`, `work`, and `watch` therefore remain current implementation vocabulary; [the plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md) requires a replacement resolver and end-to-end denial suite before changing this axis.

## Questions before user-facing rollout

- Current member-library policy shares each Bear-owned hat's reviewed memory with every Bear member. Is a person-private hat needed before user-facing setup? Do not promote a person's raw note to this shared audience silently.
- How should member semantic search recheck candidate IDs against canonical SQLite and reconstruct safe snippets before being enabled? What reviewed owner/participant policy should resolve legacy NULL-owner conversations and quarantined session-ID collisions without treating a client-session association as proof of ownership?
- Which historical profile-local records have a verifiable source ID, and how will ambiguous records remain reviewable without automatic promotion?
- How does changing a hat's resources or Work eligibility invalidate active run authority and trigger review of already-curated memory?
