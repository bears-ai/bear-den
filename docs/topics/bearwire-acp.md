## Current behavior

Den owns run and obligation state; BearWire carries it to the armature, which projects ACP and executes client-owned tools. Den-hosted tools such as `web_fetch` execute in Den, even when the human supplies their permission through ACP. At `run.start`, Den checks the authenticated human, canonical conversation, and live Work-run binding before deriving the typed armature-conversation or authorized-Work-run origin that controls client tool advertisement and the session-mode permission envelope. A client-supplied mode or descriptor list cannot manufacture an armature or Job grant. The verified origin also enters native model-tool merging; descriptor role metadata and prompt/budget selection still use a profile derived from it. Client-result continuations select the current Bear runtime binding from Den-owned Work-run state rather than assuming Pair; native turns retain their originating compatibility profile, recheck live Work eligibility, and reject mismatched bindings before invoking an approved Den-hosted tool. A one-time approval of Den-hosted `web_fetch` binds to the exact native continuation request and URL, is consumed once, and does not leave a reusable Bear-wide approval; redirects are not followed. The armature presents `Just this time` for an interactive permission request and no longer offers, saves, or reuses a global network approval across URL hosts. Den now rejects a BearWire `AllowHost` or `AllowSiteAccount` decision for `web_fetch` rather than persisting a Bear-wide approval; clients must choose the one-time decision until hat-owned persistence and its UI are connected. Its narrower remembered host/account and local-tool approvals remain client-owned and are not yet hat grants. Other runtime and execution paths retain profile-based decisions, so this edge is not a completed stance removal. For implementation-level authority and transitions, use the [state-machine inventory](../architecture/den-state-machine-inventory.md) and the [BearWire compatibility guide](../../services/den/docs/guides/bearwire-compatibility.md). For diagnosis, use [ACP troubleshooting](../guides/acp-troubleshooting.md).

## Intended behavior and gaps

The [hat access plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md#gate-0a--hat-owned-tool-and-network-permissions-accepted-target-not-deployed) makes Den's canonical hat policy the owner of persistent tool and network permissions. For an interactive action the armature should project `Just this time` (one exact obligation, no remembered grant) and `Always for [hat]` intersected with the relevant workspace, directory, command, host, or account scope. The latter requires hat-policy management authority and must disclose that eligible future Job runs can use it. The armature's local approval cache is not a second authority. A Bear admin can now configure an exact HTTPS-host and `web_fetch` tool grant on a hat; Den consults both for a bound owner's fetch, but native ACP still asks per call even when the grant exists. Configured-hat `web_search` checks the creator, membership, search-tool grant, and exact Brave provider-host grant before provider egress; it may still be advertised even when those grants are absent. A truthful no-prompt `Always for [hat]` decision and the remaining approval surfaces need the planned cutover.
