## Current behavior

### Den-owned session lifecycle

BearWire is the required Den–armature transport; the legacy `/acp/**` fallback is retired. The ordinary adapter requires Den's typed session projection, not a guess from a conversation identifier or a local activity flag.

`session.access` contains `state` and `may_select_hat`:

| State | Meaning for the ACP surface |
|---|---|
| `awaiting_hat` | An owner-bound client session exists, but no admitted durable conversation/history binding. Select a valid hat before productive work. |
| `executable` | Den currently verifies an executable canonical source. Every effect still rechecks authority; this projection is not a grant. |
| `read_only` | Authorized source-history inspection without execution authority. No productive prompt, hat selection, focus, compaction, or mode/model mutation. |

A valid IDE default can admit a new session's durable conversation on first open. Otherwise, Den keeps it pending until a valid explicit selection. `hats.list`, session/model inspection, and reconnect do not materialize pending history, even if an IDE default was configured after the initial open. Existing unbound, archived, null-owner, or another owner's history is not promoted by inspection; authorized Bear-admin inspection preserves the exact canonical source without executing as its owner or changing its hat/model configuration.

An unknown explicitly requested history target is rejected, not converted into a fresh session; an explicit provisional new-source request is a different operation. Reconnect and direct `run.start` cannot substitute an owned or fresh transcript for a session bound to read-only history. Startup checks both stored and resolved sources and preserves the existing binding on denial.

The armature treats session/conversation IDs as **opaque**, uses Den's explicit `history_conversation_id` for replay, and forwards Den's canonical binding on subsequent requests. `session/load` replays persisted visible history and available typed surface records; `session/resume` restores without replay. Pending sessions have no history to replay. Read-only lifecycle replies expose access in `_meta.bears.access`, omit modes, and return no config options. `session/list` uses the real `client_session_id`, not the database row ID. Failed load/resume does not fabricate a new session or replace a known binding with one.

`/hat` listing and diagnostics leave selection eligibility intact. An initial prompt or explicit selection holds an in-flight reservation so a competing selection cannot race it; failures release the reservation. Invalid hats and rejected admission remain retryable if Den still projects `may_select_hat: true`. Successful explicit selection or an admitted productive interaction closes the armature's initial selection opportunity before terminal delivery, so later delivery failure does not reopen it. A successful restore refreshes eligibility from Den. Load/resume cannot clear an ongoing initial prompt/selection reservation: it rejects while that interaction is reserved and fences productive/configuration/selection requests while restoring. Session-generation checks reject delayed stale responses before projecting fetched history or replacing caches/eligibility. Den remains the authority and rejects stale selection requests independently.

### Atomic source publication

Pending-to-canonical publication now creates the conversation/owner/hat binding and publishes the resolved source in the **same transaction under the client-session row lock**. Competing starts or start-versus-hat selection use the winning canonical source or fail; they do not create an orphan source or overwrite the winning hat. Direct initial starts without a session row use a separate short transaction-scoped publication lock, independent of focused-task locks. Metadata writes compare against the latest canonical source and preserve its resolved binding rather than trusting a stale pending alias.

This atomicity covers **source publication only**. It is not a lock held across inference and does not change the Work preflight/revocation limits below.

### Exact headless Work startup and compatibility

Den's BearWire `initialize` advertises `capabilities.session_access: true` and `capabilities.expected_work_source: true`. Ordinary token preflight may accept an older BearWire v1 server without those additive capability flags, but lifecycle decoding requires a valid access projection and fails closed if it is missing, malformed, foreign, or inconsistent.

Headless Work requires `expected_work_source: true` **before checkout**, not merely before a model turn. It validates checkout success, an allowed gate with a Work-run binding, the exact requested Work-run UUID in both response and binding, a non-nil execution-attempt UUID, a positive fence epoch, and a non-empty prompt. It then supplies the typed `expected_work_source` object (`work_run_id`, `execution_attempt_id`, `fence_epoch`) on both `session.open` and `run.start`, outside transcript text and client-context blobs.

That expectation identifies the exact checked-out source; it cannot grant authority. Den rechecks the live Work/session/actor, Job/hat/surface eligibility, execution attempt, and fence before admission and at subsequent startup boundaries. A mismatch detected by these checks fails rather than silently becoming an ordinary conversation using an IDE default.

Work authorization is independent of transcript authorization: an existing transcript must also be owned by the actor, active, and free of an archive marker. A live Work run or admin history visibility cannot override another owner's, null-owner, or archived transcript. Exact-source startup also fails closed rather than reusing an already-active turn whose original Work source/attempt/fence is unproven; a current session-to-Work association is not proof of that turn's admission.

**This is startup preflight with rechecks, not an atomic inference lease.** The checks do not hold attempt/hat authority across inference and do not guarantee instantaneous attempt or hat revocation. Authority may change after a successful check; rejection when observed at a recheck is not a continuous revocation guarantee. **Upgrade Den and armature together** for this boundary. The [compatibility guide](../../services/den/docs/guides/bearwire-compatibility.md) distinguishes Den's startup capabilities from the armature manifest validated at checkout.

### Run, obligation, and scoped-permission authority

Den owns run and obligation state; BearWire carries it to the armature, which projects ACP and executes client-owned tools. Den-hosted tools such as `web_fetch` execute in Den, even when the human supplies their permission through ACP. At `run.start`, Den checks the authenticated human, canonical conversation, and live Work-run binding before deriving the typed armature-conversation or authorized-Work-run origin that controls client tool advertisement and the session-mode permission envelope. A client-supplied mode or descriptor list cannot manufacture an armature or Job grant. The verified origin also enters native model-tool merging. Native Chat now keeps the same origin-eligible Den tool roster across prompt wording instead of hiding the tools for apparently informational prompts; descriptor role metadata and prompt/budget selection still use a profile derived from the origin. BearWire `run.start` and client-result continuations derive native binding IDs from the checked canonical conversation or exact live Work run rather than registered Pair/Work profiles. Native turns retain their verified origin and originating compatibility profile; before an approved Den-hosted tool, the runtime checks the same active owner-scoped conversation and editor session, or the exact live eligible Work run, and rejects a mismatched binding. Server-tool and approved Den-tool continuation policy is now compiled from the retained origin. A Work continuation also requires the exact original Work-run ID to match the current live run; the direct invoker rejects a context profile that conflicts with the origin-derived policy. The native core dispatcher selects descriptor audiences from that verified origin without registered-profile authority for ordinary calls; internal Curate/Watch calls and internal-role continuations still require registration, and legacy entry points still use profile filtering. A one-time approval of Den-hosted `web_fetch` binds to the exact native continuation request and URL, is consumed once, and does not leave a reusable Bear-wide approval; redirects are not followed. The armature presents `Just this time` for an interactive permission request. URL-targeted client-local actions offer only a one-time approval or denial: the armature does not save or reuse old host, account, or global URL approvals, and rejects stale host/account option selections. For a Den-owned `web_fetch` with a valid HTTPS destination, a verified current-hat Bear admin can additionally choose `Always for [hat]: HTTPS host [host]`, explicitly including future conversations and eligible Jobs wearing that hat. Den rejects legacy BearWire `AllowHost` and `AllowSiteAccount` decisions for `web_fetch`; the new typed `AllowHatHost` is resolved from the stored obligation and creates the canonical hat tool+host pair atomically only for the winning result. Subsequent native Pair calls skip ACP only while the live grants remain, and the effect rechecks ownership, blocks, and network safety. Before any client-local approval or reuse, the armature now asks Den for the authenticated session's hat directory. Only a verified no-hat Bear may offer/reuse its legacy Bear/client remembered filesystem and command scopes. If hats exist or the lookup fails, it clears that identity's cached approvals and cannot auto-approve from the cache. Unverifiable sessions offer only `Just this time` or denial; a verified current-hat Bear admin may additionally receive a Den-owned permanent choice for an eligible exact-root read-only filesystem action. Den can now store an admin-managed, normalized workspace-root grant for a descriptor-owned read-only filesystem action, with Bear/hat/owner checks and revocation. An authenticated `hats.workspace_tool.check` BearWire read now answers only for the current owner's Bear-scoped IDE session, its bound hat, one supported read-only filesystem descriptor, and an exact normalized root recorded for that current editor session; another member's session, a closed or archived session, another hat/root, revocation, or a Work session cannot borrow it. Bear admins can now add/revoke those exact-root read-only grants on the Hats page. The armature consults Den afresh before auto-approving an existing grant and again immediately before executing the local tool; this path is interactive editor-only and Den rejects Work sessions, its own canonical-root, symlink, and sensitive-path checks must also pass. A denied or unverifiable check falls back to a one-time ACP request, never to a local remembered approval. For a verified current-hat Bear admin, an eligible Den-owned read-only filesystem permission obligation can now offer `Always for [hat]: [read action] in [exact editor root]`, identifying future editor conversations and explicitly excluding Work. BearWire derives its action from the persisted tool obligation, requires the root to be recorded on the active owner-scoped session, and inserts the winning permission result and scoped grant in one Postgres transaction under the current admin/hat locks. A failed write rolls back the claim; another member may still choose a one-time approval. Duplicate or stale replies cannot regrant, and the armature rechecks the grant before executing the resulting local tool. The separate armature-local fallback prompt cannot turn a stale permanent option into a one-time action. Bear admins can also configure the same grant in Hats. This permanent ACP option does **not** extend to writes, commands, MCP, arbitrary URLs, or Work sessions. The armature now also rejects filesystem targets whose existing path or closest existing ancestor resolves through a symlink outside its workspace roots; filesystem race-free handle-based enforcement remains separate. Other network actions and directory/command scopes remain open. The former `/internal/den-tools/invoke` HTTP entry point has been removed; its caller-supplied context could not prove a verified origin even with a service token. Some executor internals and legacy entry points still use profiles, so this is not a completed stance removal. For implementation-level authority and transitions, use the [state-machine inventory](../architecture/den-state-machine-inventory.md) and the [BearWire compatibility guide](../../services/den/docs/guides/bearwire-compatibility.md). For diagnosis, use [ACP troubleshooting](../guides/acp-troubleshooting.md).

## Intended behavior and gaps

The [hat access plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md#gate-0a--hat-owned-tool-and-network-permissions-partial-cutover-exit-pending) makes Den's canonical hat policy the owner of persistent tool and network permissions. For an interactive action the armature should project `Just this time` (one exact obligation, no remembered grant) and `Always for [hat]` intersected with the relevant workspace, directory, command, host, or account scope. The latter requires hat-policy management authority and must disclose whether eligible future Job runs can use it; the currently supported editor workspace-read choice explicitly excludes Work. The armature's local approval cache is not a second authority. A Bear admin can configure an exact HTTPS-host and `web_fetch` tool grant on a hat, either from the Hats page or the narrowly scoped ACP choice. Native Pair web fetches with both grants no longer ask per call; Den still rechecks at execution. Configured-hat `web_search` checks the creator, membership, search-tool grant, and exact Brave provider-host grant before provider egress. The next native Pair model roster now omits it without those grants or when the provider is blocked/unconfigured, including if a client attempts to forward a matching descriptor; other capability catalogs are not yet filtered by the same resolver. The remaining ACP action families and client-local approval surfaces need the planned Den-owned cutover.
