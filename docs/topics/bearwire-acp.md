# BearWire and ACP

**Owner:** Den BearWire + Armature code owners.
**Scope:** Interactive Den–armature sessions and their ACP client projection.
**Current as of:** 2026-10-01; evidence: `services/den/crates/den-bearwire/src/methods/run.rs`, `services/den/crates/den-bearwire/src/methods/tests.rs`, `services/den/crates/den-core/src/client_tools.rs`, `services/den/crates/den-core/src/effective_policy/tests.rs`, `tools/bear-armature/`, and `tests/smoke/test_stack.py`.

## Current behavior

Den owns run and obligation state; BearWire carries it to the armature, which projects ACP and executes client-owned tools. Den-hosted tools such as `web_fetch` execute in Den, even when the human supplies their permission through ACP. At `run.start`, Den checks the authenticated human, canonical conversation, and live Work-run binding before deriving the typed armature-conversation or authorized-Work-run origin that controls client tool advertisement and the session-mode permission envelope. A client-supplied mode or descriptor list cannot manufacture an armature or Job grant. The verified origin also enters native model-tool merging. Native Chat now keeps the same origin-eligible Den tool roster across prompt wording instead of hiding the tools for apparently informational prompts; descriptor role metadata and prompt/budget selection still use a profile derived from the origin. Client-result continuations select the current Bear runtime binding from Den-owned Work-run state rather than assuming Pair; native turns retain their verified origin and originating compatibility profile, recheck live Work eligibility, and reject mismatched bindings before invoking an approved Den-hosted tool. Server-tool and approved Den-tool continuation policy is now compiled from the retained origin. A Work continuation also requires the exact original Work-run ID to match the current live run; the direct invoker rejects a context profile that conflicts with the origin-derived policy. The native core dispatcher now selects descriptor audiences from that verified origin; its registered-profile check remains a consistency gate, while legacy entry points still use profile filtering. A one-time approval of Den-hosted `web_fetch` binds to the exact native continuation request and URL, is consumed once, and does not leave a reusable Bear-wide approval; redirects are not followed. The armature presents `Just this time` for an interactive permission request. URL-targeted client-local actions offer only a one-time approval or denial: the armature does not save or reuse old host, account, or global URL approvals, and rejects stale host/account option selections. For a Den-owned `web_fetch` with a valid HTTPS destination, a verified current-hat Bear admin can additionally choose `Always for [hat]: HTTPS host [host]`, explicitly including future conversations and eligible Jobs wearing that hat. Den rejects legacy BearWire `AllowHost` and `AllowSiteAccount` decisions for `web_fetch`; the new typed `AllowHatHost` is resolved from the stored obligation and creates the canonical hat tool+host pair atomically only for the winning result. Subsequent native Pair calls skip ACP only while the live grants remain, and the effect rechecks ownership, blocks, and network safety. Before any client-local approval or reuse, the armature now asks Den for the authenticated session's hat directory. Only a verified no-hat Bear may offer/reuse its legacy Bear/client remembered filesystem and command scopes. If hats exist or the lookup fails, it clears that identity's cached approvals, offers only `Just this time` or denial, rejects stale persistent choices, and cannot auto-approve from the cache. Den can now store an admin-managed, normalized workspace-root grant for a descriptor-owned read-only filesystem action, with Bear/hat/owner checks and revocation. This storage is **not** a permission to execute: ACP does not yet offer a persistent Den-owned `Always for [hat]` choice for client-local tools, and neither BearWire nor the armature consumes that workspace grant at execution. Other network actions and directory/command scopes remain open. The former `/internal/den-tools/invoke` HTTP entry point has been removed; its caller-supplied context could not prove a verified origin even with a service token. Some executor internals and legacy entry points still use profiles, so this is not a completed stance removal. For implementation-level authority and transitions, use the [state-machine inventory](../architecture/den-state-machine-inventory.md) and the [BearWire compatibility guide](../../services/den/docs/guides/bearwire-compatibility.md). For diagnosis, use [ACP troubleshooting](../guides/acp-troubleshooting.md).

## Intended behavior and gaps

The [hat access plan](../roadmap/HATS_AND_SESSION_MEMORY_BOUNDARIES_PLAN.md#gate-0a--hat-owned-tool-and-network-permissions-partial-cutover-exit-pending) makes Den's canonical hat policy the owner of persistent tool and network permissions. For an interactive action the armature should project `Just this time` (one exact obligation, no remembered grant) and `Always for [hat]` intersected with the relevant workspace, directory, command, host, or account scope. The latter requires hat-policy management authority and must disclose that eligible future Job runs can use it. The armature's local approval cache is not a second authority. A Bear admin can configure an exact HTTPS-host and `web_fetch` tool grant on a hat, either from the Hats page or the narrowly scoped ACP choice. Native Pair web fetches with both grants no longer ask per call; Den still rechecks at execution. Configured-hat `web_search` checks the creator, membership, search-tool grant, and exact Brave provider-host grant before provider egress. The next native Pair model roster now omits it without those grants or when the provider is blocked/unconfigured, including if a client attempts to forward a matching descriptor; other capability catalogs are not yet filtered by the same resolver. The remaining ACP action families and client-local approval surfaces need the planned Den-owned cutover.
