## Current behavior

Docket owns canonical jobs and tasks in Den Postgres. Client-session task attachments are distinct from the `pair` stance; execution authority is bound to tasks, attempts, and runs rather than to that label. Start with [tasks and autonomy](../architecture/tasks-and-autonomy.md) for the conceptual model and [the state-machine inventory](../architecture/den-state-machine-inventory.md) for authority boundaries. The `den-docket` crate owns persistence and the service API. BearWire Git-commit artifacts attached to a task carry the origin of their canonical live Work run or focused Pair execution attempt; the model's label does not decide their owner profile. For newly provisioned hat-bound Work sandboxes, Den checks the eligible Job/hat and selected managed surface before task start, then supplies the intersection of that hat's exact HTTPS-host grants and the work surface's outbound-host ceiling. Before starting the task or minting a token, Den requires a healthy provider advertising both run-scoped ceilings and Den-checked per-connection egress; old or unreachable providers fail closed for hat-bound Work. The provider re-intersects against its saved root and rejects open-network requests carrying a per-run ceiling. For restricted-network sandboxes, it now resolves every allowed external hostname before relay startup, rejects empty or mixed public/private answers, and pins a vetted public IPv4 for the relay's upstream while preserving the approved DNS alias for TLS SNI. Hosts without public IPv4 or with a DNS lookup that exceeds ten seconds fail closed. No-hat runs retain legacy surface-only authorization, but their restricted-network relays also use the same DNS pinning. For hat-bound running/reporting Work runs, the worker records the provisioned host ceiling and rechecks current Job/hat/surface policy on each poll. A lost grant, changed surface, ineligible Job, or missing pre-cutover snapshot requests cancellation, revokes the run token, and attempts provider teardown; a failed teardown leaves the run cancellable for retry instead of marking a possibly reachable relay terminal. For a newly provisioned hat-bound run, each new external HTTPS relay connection now asks Den's BearWire `work.egress.check`: it authenticates the run-minted Bear token, requires the same live uncancelled sandbox run, Job creator, current non-revoked Job run, and intersects the exact host with its provisioned snapshot and current hat/work-surface grants. Den denial, missing run context, a revoked token/grant, or a Den outage closes the connection before it dials the pinned host. Old sandbox images without the guarded relay fail before connection to the task network; no-hat relays retain their pinned-host legacy path. An existing authorized TCP connection can continue until its 60-second hard lifetime ends (or the worker polls and tears down the provider); this is per-connection, **not per-HTTP-request** revocation. The base sandbox image and upgraded provider image built locally, and an unprivileged relay listener and mocked Den allow/deny/outage checks passed. The optional provider service is not running locally, so a real Job sandbox/relay revocation flow remains unverified. Provider-owned git upstream operations remain a separate boundary. The hosted Cargo dependency-preparation helper is another separate outbound path: it runs on an unrestricted Docker bridge for no-hat legacy Work. Until that helper has grant-enforced network isolation, Den rejects the model-facing helper for hat-bound Work and removes it from new hat-bound Work model tool rosters. The provider also rejects hat-bound Rust workspaces at provisioning before its automatic unrestricted Cargo fetch starts. This prevents those Jobs from provisioning until dependency preparation has a grant-enforced network route; the relay policy does not make the separate Cargo helper safe.
