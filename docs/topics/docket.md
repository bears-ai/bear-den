## Current behavior

Docket owns canonical Jobs, tasks, and client-session task attachments in Den Postgres. Execution authority is bound to verified sources, tasks, attempts, and runs. Docket questions additionally require session-task capability at the Den tool boundary and a live, owned human client session, canonical active conversation, and current Bear membership at Docket insertion; a live Work-bound session or an audit `actor_role` label cannot substitute for that source. Start with [tasks and autonomy](../architecture/tasks-and-autonomy.md) for the conceptual model and [the state-machine inventory](../architecture/den-state-machine-inventory.md) for authority boundaries. The `den-docket` crate owns persistence and the service API. BearWire Git-commit artifacts attached to a task carry the origin of their canonical live Work run or focused Pair execution attempt; the model's label does not decide their owner profile. For newly provisioned hat-bound Work sandboxes, Den checks the eligible Job/hat and selected managed surface before task start, then supplies the intersection of that hat's exact HTTPS-host grants and the work surface's outbound-host ceiling. Before starting the task or minting a token, Den requires a healthy provider advertising both run-scoped ceilings and Den-checked per-connection egress; old or unreachable providers fail closed for hat-bound Work. The provider re-intersects against its saved root and rejects open-network requests carrying a per-run ceiling. For restricted-network sandboxes, it now resolves every allowed external hostname before relay startup, rejects empty or mixed public/private answers, and pins a vetted public IPv4 for the relay's upstream while preserving the approved DNS alias for TLS SNI. Hosts without public IPv4 or with a DNS lookup that exceeds ten seconds fail closed. No-hat runs retain legacy surface-only authorization, but their restricted-network relays also use the same DNS pinning. For hat-bound running/reporting Work runs, the worker records the provisioned host ceiling and rechecks current Job/hat/surface policy on each poll. A lost grant, changed surface, ineligible Job, or missing pre-cutover snapshot requests cancellation, revokes the run token, and attempts provider teardown; a failed teardown leaves the run cancellable for retry instead of marking a possibly reachable relay terminal. For a newly provisioned hat-bound run, each new external HTTPS relay connection now asks Den's BearWire `work.egress.check`: it authenticates the run-minted Bear token, requires the same live uncancelled sandbox run, Job creator, current non-revoked Job run, and intersects the exact host with its provisioned snapshot and current hat/work-surface grants. Den denial, missing run context, a revoked token/grant, or a Den outage closes the connection before it dials the pinned host. Old sandbox images without the guarded relay fail before connection to the task network; pre-gateway hat-run snapshots request cancellation on the next owning worker poll. No-hat relays retain their pinned-host legacy path. An existing authorized TCP connection can continue until its 60-second hard lifetime ends (or the worker polls and tears down the provider); this is per-connection, **not per-HTTP-request** revocation. The base sandbox image and upgraded provider image built locally, and an unprivileged relay listener and mocked Den allow/deny/outage checks passed. The optional provider service is not running locally, so a real Job sandbox/relay revocation flow remains unverified. Provider-owned git upstream operations remain a separate boundary. The hosted Cargo dependency-preparation helper is another separate outbound path: it runs on an unrestricted Docker bridge for no-hat legacy Work. Until that helper has grant-enforced network isolation, Den rejects the model-facing helper for hat-bound Work and removes it from new hat-bound Work model tool rosters. The provider also rejects hat-bound Rust workspaces at provisioning before its automatic unrestricted Cargo fetch starts. This prevents those Jobs from provisioning until dependency preparation has a grant-enforced network route; the relay policy does not make the separate Cargo helper safe.

Job creation requires an explicit, non-deserializable `DocketJobCreationAuthority`: an authenticated human UI request or a native turn carrying verified origin and governance. Native requests require `CreateJob` from that policy; Work, curation, observation, and noninteractive turns cannot create Jobs by claiming a human audit label. The creation transaction locks and rechecks the creator's current Bear membership before writes, including hat-bound creation. `created_by_role` is nonempty audit provenance, not permission; the SQL schema accepts provenance independently of execution origin. Hat eligibility, surface bounds, source ownership at native invocation, and Job/run checks remain separate requirements.

## Mission knowledge and saved evidence

**Verified 2026-10-05 in the local branch:** a Job owner or Bear admin can link/clear an accessible Cabinet page from Job detail. Docket owns the optional `cabinet_ref` and revision in `job_cabinet_refs`; Cabinet owns the page, content and access, not Job state. A Mission is an ordinary page, not a new container or ID space. Saving a stale annotation revision fails rather than overwriting it. Job views omit unreadable page refs/titles.

**Save a private copy** captures the selected exact published Cabinet version in a `cabinet_document_snapshot` JSON artifact and attaches it as Job source evidence atomically. The payload records typed page/version refs, captured title, Markdown content and content hash. Later page edits or deletion do not alter the copy. Capture does not change Job status or expose private content to Work. Job detail lists readable saved document evidence and provides downloads that recheck Job visibility, link ownership and artifact access; another Job's route cannot download it. The copy remains private to its creator under current Bear membership even if the Job is shared. Source-page access changes do not revoke a previously authorized private copy.

Evidence: `den-docket/src/missions.rs`, `den-service/src/cabinet/snapshots.rs`, `den-web/src/work/knowledge.rs`, and database-backed `den-web/src/work/tests/knowledge.rs`. All 120 web tests pass, including the expanded Mission/evidence flow, and the production image is rebuilt and healthy locally. The wider `den-docket --lib` suite is not green: 102 pass and 12 session/dispatch/work-run tests fail; the exact same failure set reproduces with HEAD application code on the same migrated database. These unrelated failures remain unresolved. See the [Cabinet guide](../guides/cabinet.md#attachments-and-private-copies) for retention and upload limitations.
