## Current behavior

Docket owns canonical jobs and tasks in Den Postgres. Client-session task attachments are distinct from the `pair` stance; execution authority is bound to tasks, attempts, and runs rather than to that label. Start with [tasks and autonomy](../architecture/tasks-and-autonomy.md) for the conceptual model and [the state-machine inventory](../architecture/den-state-machine-inventory.md) for authority boundaries. The `den-docket` crate owns persistence and the service API. BearWire Git-commit artifacts attached to a task carry the origin of their canonical live Work run or focused Pair execution attempt; the model's label does not decide their owner profile. For newly provisioned hat-bound Work sandboxes, Den checks the eligible Job/hat and selected managed surface before task start, then supplies the intersection of that hat's exact HTTPS-host grants and the work surface's outbound-host ceiling. Before starting the task or minting a token, Den requires a healthy provider advertising support for run-scoped ceilings; old or unreachable providers fail closed for hat-bound Work. The provider re-intersects against its saved root and rejects open-network requests carrying a per-run ceiling. For restricted-network sandboxes, it now resolves every allowed external hostname before relay startup, rejects empty or mixed public/private answers, and pins a vetted public IPv4 for the relay's upstream while preserving the approved DNS alias for TLS SNI. Hosts without public IPv4 or with a DNS lookup that exceeds ten seconds fail closed. No-hat runs retain legacy surface-only authorization, but their restricted-network relays also use the same DNS pinning. For hat-bound running/reporting Work runs, the worker records the provisioned host ceiling and rechecks current Job/hat/surface policy on each poll. A lost grant, changed surface, ineligible Job, or missing pre-cutover snapshot requests cancellation, revokes the run token, and attempts provider teardown; a failed teardown leaves the run cancellable for retry instead of marking a possibly reachable relay terminal. This is **not** per-connection gateway authorization: a relay can remain usable until the next poll and successful provider teardown. Den now has a BearWire `work.egress.check` decision for an exact new connection: it authenticates the run-minted Bear token, requires the same live uncancelled sandbox run and Job creator, and intersects the requested exact HTTPS host with its provisioned snapshot and current hat/work-surface grants. Existing provider relays do not call it, so this decision alone does not change live network effects or eliminate the revocation window. Provider-owned git upstream operations remain a separate boundary. The hosted Cargo dependency-preparation helper is another separate outbound path: it runs on an unrestricted Docker bridge for no-hat legacy Work. Until that helper has grant-enforced network isolation, Den rejects it for hat-bound Work and removes it from new hat-bound Work model tool rosters. This can prevent dependency preparation in those Jobs; it does not turn the helper into a safe hat network route.
