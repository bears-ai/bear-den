# Hats and session memory boundaries

**Status:** Active
**Topic:** [Bear memory and hats](../topics/bear-memory-hats.md).

Implementation started: a Bear-owned hat schema, typed hat ID, internal create/list/allow-surface functions, and guarded canonical conversation/Job binding and current-eligibility lookup have database tests. Per-Bear SQLite can now store distinct source-local and hat-scoped records and migrate old profile-local rows without promoting them; storage tests cover new and upgraded databases. Bear-admin routes now create and configure hats, start an owner-scoped hat-bound chat, bind an empty inactive conversation once, and bind an eligible draft Job once; bound turns already use hat bindings for memory. Enabling Work requires a permitted surface: an empty hat passes directly, while a populated hat requires a complete Bear-admin review of its historical memory with an auditable snapshot receipt. Populated hats with up to 500 historical records can be reviewed 100 at a time, with a shared full-snapshot fingerprint and a final-page acknowledgement; hats above this bounded limit remain blocked. New opt-in scoped SQLite read/browse/keyword functions filter on canonical columns and apply the existing access-bearing entity rules; denial tests include a path collision with legacy records and a confined note. The legacy model-facing direct read now enforces its advertised profile/core wall on each record, fixing guessed cross-profile paths; the admin read remains separate. A Den-owned resolver now distinguishes legacy sessions from bound canonical conversations/Work runs and refuses to downgrade a Work run after hat eligibility is revoked. A separate vector filter expresses the same source/hat/core restriction, but new scope types are deliberately not indexed while member semantic search lacks canonical hit rechecking. Bound conversations and eligible Work runs now route model-facing memory writes/reads/browse/keyword search using the canonical grant, with a Postgres-backed two-conversation test of persistence and next-tool access. Bound turn-start projection replaces legacy profile highlights with source/hat highlights and scoped recall; derived hits are rechecked against SQLite before rendering, including stale archive and path-collision cases. Bears without hats still use legacy profile-local memory; on a configured Bear, unbound human conversations are denied before an ordinary turn and unbound Work runs are denied at checkout and before sandbox provisioning (as well as turn start), while owner-authorized historical transcripts remain readable. New scopes are deliberately not indexed for member semantic search, and routine `curate` promotion and review of hats beyond the 500-record bound are not shipped. The approved Den-tool continuation path preserves its Work-run ID. Bound prompt-memory selection and list/upsert/patch tools now admit Bear-wide reads and exact-client-session blocks only, with mutations limited to the current session. Postgres upserts cannot reassign a block ID to another Bear or scope, and patches are Bear/profile constrained. Scoped `memory_status` and `session_info` avoid exposing legacy profile counts or labels; bound turns ignore opaque supplied runtime context in favor of Den compilation. This is a *human-turn cutover*, not completion of Bear-wide session isolation: historical unbound memory and internal non-human paths need review, alongside routine `curate` promotion, review beyond the bounded 500-record snapshot, retrospective memory import, historical ownerless conversations, and ambiguous client-session IDs still need explicit policy before a complete hat rollout. The ordinary member memory library now admits only canonical shared and Bear-owned hat records, with direct-ID/history enforcement and access-bearing checks; raw entity and reflection/proposal inspection is admin-only. Member semantic search falls back to curated keyword until its derived hits have a canonical SQLite recheck. The browser chat now exposes a separate owner-verified, source-only read of current private conversation notes (up to 50) without widening the shared memory library or admin transcript reads. This plan tests a simpler Bear mental model rather than committing to a hat-first platform migration. The [topic](../topics/bear-memory-hats.md) distinguishes current behavior from the target. A hat is a configured responsibility and resource/capability *limit*; it is neither another Bear nor a replacement for a Job, Mission, work surface, Connection, or governance state. Canonical cognition remains in per-Bear SQLite. Transcripts, Docket state, prompt-memory blocks, and derived recall are distinct state owners. Do not add another writable copy of hat permissions or memory.

## Current audience-boundary progress (branch behavior)

- Hat identity text now has a canonical Bear-owned Postgres field and Bear-admin editor/escaped component preview. Existing hats were initialized from their purposes and new hats start with their purpose. The prompt cutover resets preexisting Work-enabled hats to Work off rather than sharing a previously unreviewed identity with autonomous Work; admins must explicitly re-enable after reviewing identity and (if populated) historical hat memory. Existing Jobs lose Work eligibility while off; old memory-only receipts remain historical and rollback does not restore Work grants. Identity and memory fingerprints are both rechecked under the existing hat/SQLite locks, with the identity hash stored on new review receipts. Editing a Work-enabled hat requires a Work-audience acknowledgement. Hat-bound `chat`/`pair`/`work` turn assembly now uses that verified hat identity plus a compiled Bear-wide base and repository-owned mode instructions, without selecting legacy per-stance identity contracts. A changed hat takes effect on the next turn; managed bound components check their repository source version before reuse. A configured Bear with no verified conversation/Work binding fails closed at assembly. No-hat Bears and internal `curate`/`watch` retain their legacy prompt paths; detailed internal-role identity and eventual stance reduction remain to decide.
- Bear admins may designate one IDE default hat for a Bear; the preference is a nullable Bear-owned hat ID, not another writable hat flag or a per-connection authority grant. A new ACP/BearWire IDE session materializes its owner-scoped canonical conversation before its first turn and binds the default if present. The Bear-level armature connection remains the identity boundary. Bare `/hat` lists choices; `/hat <name or UUID>` is an armature-local first-interaction override checked again by Den against the canonical conversation, human owner, and prior activity. Reconnect does not change the stored hat. A Bear with no default starts unbound and cannot take an ordinary turn once hats exist until a hat is chosen before the first turn; a Bear with no hats retains legacy turns. Work continues to derive its hat from the Job. Ordinary members can now choose a hat when creating a browser conversation; when a Bear has hats, new UI-created Jobs require a Work-enabled hat that covers their surfaces, bound atomically at Job creation. Bears without hats retain the legacy unbound creation path.

- Canonical human conversation access now checks current Bear membership and Postgres `conversations.created_by_user_id`; ordinary members are limited to their own source, Bear admins can inspect legacy ownerless rows. On a configured Bear, browser send and BearWire `run.start` reject unbound conversations before a user turn or run is persisted, and unbound Work runs cannot resolve profile memory. The browser marks historical unbound threads read-only without hiding owner/admin history. The automatic dispatcher skips ineligible Jobs before enqueueing, and the dispatch worker and BearWire Work checkout recheck the same Den-owned Job/hat/surface memory binding before starting tasks, minting tokens, provisioning sandboxes, or binding execution attempts; this is not a second historical-memory review. The default chat is offered as a writable synthetic thread only when the Bear has no hats. Browser chat list/history/artifacts/model/mutation/send, BearWire history/session/run, and management inspection pages use this boundary. A browser `default` is resolved per human and a new chat receives a durable owner-scoped ID before persistence. User-visible transcript projection excludes diagnostic/admin/model-only tool rows; model replay uses a separate projection. Non-admins cannot inspect broad activity, prompt-memory context, reflection evidence, or stance diagnostics through Bear management pages.
- Human Work Job visibility is owner/admin or explicitly `BearVisible`. Docket job/task checkout and human task-list sync, model-facing job tools, current-task selection, Work web read/control paths, BearWire Docket RPCs, focused task activation, and Work checkout enforce the job/task owner boundary. A different member's sandbox checkout of a shared job needs the exact run-minted token, not just a known run ID. BearWire event and focused-transition pagination filters by Bear/user/session before limiting.
- Work enablement is a hat-configuration transition, not a run-start check: an empty hat can enable after its identity is explicitly reviewed; a populated hat requires that review and an explicit Bear-admin review of all historical memory, including archived/superseded records. Den compares the submitted identity fingerprint under the Postgres hat lock and the record count/memory fingerprint to a fresh SQLite snapshot under a writer lock, records a Postgres review receipt containing both fingerprints, then enables Work while holding the same locks used by curation. Review pages show 100 records each, reject changed identity or full-memory-snapshot fingerprints between pages, and require a final-page acknowledgement; incomplete snapshots (>500 historical records) still fail closed. A later run does **not** require empty memory; it still requires an authorized Job, eligible surfaces, and execution policy. Future curation into a Work-enabled hat requires a Work-audience acknowledgement. This gate does not assess Bear-wide `core/` memory, which Work may also read.
- The Postgres client-session trigger now serializes concurrent claims and refuses any new cross-user or cross-Bear reuse of an opaque session ID without dropping existing rows. The dev database still contains two historical collision groups (41 rows) and 40 NULL-owner conversations. Thirty of those conversations have only a session association, not trustworthy independent human provenance; they stay admin-only pending explicit review. Historical collisions remain quarantined, and internal session-only event joins plus post-limit Docket task/entry/run listings remain to audit. Bear admins can now manually review a verified source-local note and publish newly authored hat content with SQLite source→target provenance, optimistic replacement, and explicit Work-audience acknowledgement. This does not yet automate routine `curate` promotions or complete migration.

## Gate 0 — Verify the contract before widening runtime behavior

- Define typed authorization inputs without assuming a stance label: authenticated human/membership; immutable conversation/Job source and hat binding; actual trusted armature or channel origin; effective resource grants; approved Job/run context; Den supervision and approval state. Hat permissions can only narrow existing rights. Model text, prompts, tool results, and UI labels never grant authority. A client reconnection cannot change the durable conversation binding; a hat or work-surface change requires an explicit rebind with reevaluation. Work runs derive their hat from the assigned Job; a run may retain an immutable authorization snapshot for audit but may not keep a second writable grant.
- Define the ordinary memory read set as own source-unit uncurated records + authorized hat-curated records + Bear `core/`. No ordinary path to another session's raw memory. Only the privileged curation/review path may inspect source records across sessions, and it has no arbitrary outbound execution path. No cross-session raw access via semantic search, keyword search, direct memory read/browse, graph expansion, turn-start projection, prompt-memory blocks, exports exposed to the model, or legacy aliases.
- Do not assume `client_session_id` is a durable memory bucket: the state inventory identifies canonical conversation as the durable interactive container, distinct from client sessions. Confirm the stable Work-run and intake source IDs before writing migrations. Decide whether hat membership is Bear-wide or person-private before public rollout; the isolated prototype can use a clearly shared Bear-owned hat.
- Challenge whether a closed execution class is needed for curation, ingress, and outbound work. Do not remove `TrustProfile` first and later recreate the same boundary as ad hoc string flags. Update the state-machine inventory and the affected ADRs when a concrete authority design is accepted; this draft is not that decision.

**Proposed policy matrix to review** (describes the target, not current enforcement):

| Verified source | Ordinary memory available | Effects and hard denial |
| --- | --- | --- |
| Human conversation over a channel | Own conversation notes, hat-curated, Bear core | Den-hosted tools under channel policy; no armature-local tools without a verified armature. |
| Same conversation through a verified armature | Same notes as above | Local tools only through armature obligations/approvals; changing client connection does not change which conversation's notes are owned. |
| Interactive run after armature disconnect | Same memory owner, subject to current user/policy authorization | Governance may change; absent client cannot supply local tools or approvals. |
| Job-authorized background run | Own Work-run notes, approved hat-curated, Bear core | Only Job-scoped tools, resources, and egress; never raw notes from the originating conversation. |
| Authenticated inbound event intake | Only its own payload/source unit and authorized curated context | Can record an observation, never initiate outbound effects from the event itself. |
| Privileged curation process | Reviewable raw source notes and curated records needed for review | May promote with provenance; no arbitrary outbound execution. Not a general-purpose ordinary session. |

All ordinary rows deny other source units' uncurated memory regardless of common hat, historical profile, tool implementation, or knowledge of a record ID. This matrix deliberately does not grant permissions merely because an origin is named: Den must authenticate the source, check the hat, and enforce resource/action limits at execution. Review who may access raw notes through other human management endpoints and exports separately. The member-facing memory library now filters raw notes, but Bear admins deliberately retain an explicit broad inspection path.

**Exit:** one reviewed matrix of allowed/denied memory reads and tool/action classes for interactive channel, verified armature, disconnected continuation, approved Work run, inbound intake, and curator. A table-driven executable policy test belongs beside the authoritative typed resolver once it exists, not as a prompt-only assertion.

## Gate 1 — Set the product contract and build a prototype

Test a low-fidelity setup card for a named **Security review** hat:

> Purpose: Review security of Repository A. Resources: Repository A. While you're here: can inspect and propose edits with approval. Autonomous work: off. Memory: notes from this conversation stay here until reviewed; reviewed knowledge for this hat may be used in future conversations. Enabling autonomous work later requires reviewing the hat's existing memory first.

Use the card to settle the contract and build a narrow admin/session prototype on this pre-release branch. In automated scenarios, check that its claims match the runtime: a new conversation cannot see raw notes from another; reviewed knowledge for a shared hat can be reused; a Work run cannot act without a Job; and enabling Work requires reviewing already-curated hat memory. Keep stance names out of the ordinary UI, but expose derived denial reasons in advanced audit/diagnostics. Iterate the copy alongside the implementation rather than blocking code on external usability recruitment.

**Exit:** a working prototype and tests make the card's promises true. Later user research may improve the copy; it is not a pre-release implementation gate.

## Gate 2 — Prove one complete isolated workflow

Build the smallest real vertical slice in a dedicated test Bear: one Bear-owned hat, one bound resource, two separate conversations (one armature-backed), a source note and explicit promotion, plus a Job-bound Work run. Exercise credential/armature/Job permissions using the existing descriptor and obligation boundaries; do not turn the hat into a free-form allowlist of provider tool names. Preserve stable tool surfaces; a channel cannot manufacture armature tools by mentioning a hat.

Den Postgres owns hat configuration and conversation/Job binding; per-Bear SQLite owns canonical memory and promotion provenance. Changes to Postgres SQL use SQLx macros and timestamped `scripts/sqlx.sh migrate add` migrations; changes to per-Bear SQLite use its schema and upgrade paths. `MemoryStoreManager` is process-wide, not re-created by a new hat feature. Bind in both chat and BearWire entry points, Job creation/dispatch, `session_info`, and model context; require typed IDs rather than trusting model-supplied hat strings.

**Executable denial/allowance matrix** (test both keyword and Qdrant when configured, plus direct reads/browse and turn-start projection):

| Scenario | Expected |
| --- | --- |
| A writes private note with an unmistakable secret/injected instruction; B uses same hat and same legacy profile (including the case where B is a different Bear member) | B cannot see raw A note, even by ID/path/query/recall or the member-facing memory UI; A may read its own note after reconnect. |
| Curator promotes a safe derived fact from A to hat | B can see the curated fact with provenance, not A's raw source. |
| Different hat or Bear asks for the promoted fact | Denies hat memory (Bear `core/` remains its own separate scope). |
| Job-bound Work run uses same hat | Sees only reviewed hat/core knowledge and its own run notes; cannot fetch A or B raw memory; cannot execute unapproved actions. |
| Unverified chat claims an armature, or a disconnected armature attempts a client tool | No armature-owned execution. |
| Hat's Work eligibility or resource grants expand after curation or dispatch | Existing Work run gets no silent grant; Work-enablement requires review of existing hat memory. |

Memory passages, recall-index payloads, graph expansions, direct read paths, and human/admin endpoints must derive visibility from canonical scope; a stale derived index is never an authorization source. Test a malicious memory text that tries to impersonate policy. Curation may summarize/redact; it does not make content executable instruction or grant Job authority.

**Exit:** one end-to-end run demonstrates the above, including negative cases. Keep the slice isolated; do not roll it out to existing Bears merely because the happy path passes.

## Gate 3 — Inventory and migrate without widening access

- Inventory `profile_local` SQLite records, `memory_proposals`/promotions, imported logical paths, Den Postgres `prompt_memory_blocks`, reflection sources, and derived recall indexes. Use source provenance only when it is verifiably a canonical conversation or run ID; do not assume a client session ID survives reconnect. Preserve existing shared `core/` semantics while auditing what it contains.
- For profile-local records without verifiable source, retain a restricted legacy review/archive view. Never automatically declare them curated for a default hat or expose them to a new conversation. Plan retention/export/deletion and manual promotion; quantify how much prior continuity becomes unavailable.
- Update all SQL/SQLite/vector/keyword/graph read and write paths together. Rebuild/reconcile derived indexes and invalidate stale passages. A compatibility mode that continues to return all profile-local records to a new session is not a secure rollout.

**Exit:** restore/migration tests preserve provenance and curation outcomes without widening access; test old database files and imports, plus behavior with semantic recall disabled. Tool and UI access to archives follows explicit admin/review authorization rather than ordinary model search.

## Gate 4 — Product surface and architecture decision

- Build on the Bear-admin hat setup card, ACP first-interaction `/hat`, and ordinary browser conversation/Job selection; show active hat, own notes, pending review, hat-curated memory, and Bear-wide knowledge in Bear memory UI. Browser chat now shows its owner-only notes; a unified scope-labeled member memory view remains open. Reuse existing Bear management pages and memory library, not a duplicate memory store. Keep work surfaces/Connections as separate resource cards; extend the existing populated-hat review to paginated large hats and ensure the warnings stay legible.
- **Move identity prompts from stances to hats before reevaluating stances.** Inventory the current `context_profile.role_contracts`, managed `space_instruction.*` blocks (including Bear-admin overrides), compiled per-stance prompts, and Markdown stance fragments. Offer an explicit review/manual transfer of custom stance prose into Bear-wide or hat identity where appropriate; never copy whole stance contracts or inferred permissions into hats automatically. Separate durable Bear-wide identity from hat-specific purpose, voice, and responsibility; keep trusted runtime/interaction instructions (for example, whether a human is present, sandbox boundaries, and tool/approval behavior) platform-owned and derived from verified execution context, not from hat prose. Give Bear admins one legible hat-identity editor and preview, without making a hat prompt an authorization grant. Extend Den's context compiler to produce/revalidate the hat-specific identity component when a hat changes, and have turn assembly select it from the canonical conversation binding or Work Job—not from a client-supplied label, stance name, or memory text. The same hat must retain its identity across permitted browser, ACP, and Work uses, while each surface keeps its own enforced tool, egress, and approval limits. Explicitly decide how internal `curate`/`watch` identities are composed; do not silently apply the IDE default or invent a hat for them. Retain a clearly scoped no-hat legacy prompt path until migration is verified; prevent a configured Bear from falling back to a different stance identity when its hat identity is missing or stale. Regression tests must inspect compiled artifacts **and the next-turn model request** for two hats, the same hat across interactive and Work contexts, edits/recompilation, reconnects, missing bindings, and prompt text attempting to claim extra authority.
- Only after the workflow and hat-identity cutover are enforced, compare the existing `chat`/`pair` entry paths and `TrustProfile`/`TurnAuthority` with typed session origin, armature, Job, hat, and governance inputs. Collapse `chat`/`pair` if verified armature plus policy fully preserves their distinctions. For `work`, `watch`, `curate`, remove an authoritative stance label only where the denial matrix still passes and no hidden authority has moved into prompts, UI flags, or tool-name checks. Keep diagnostic labels if useful.
- Update the [memory model](../architecture/memory-model.md), [state-machine inventory](../architecture/den-state-machine-inventory.md), [stance conceptual reference](../architecture/bear-stances.md), and affected ADRs with verified behavior; update public descriptions only when shipped. The plan is not evidence of delivery.

**Exit:** an admin can predict memory sharing, hat identity, and action authority without stance vocabulary; verified bound turns use Bear-wide plus selected-hat identity without leaking another hat's identity or losing runtime safety instructions; regressions cover persistence, compiled prompt selection, and the next-turn model request; the decision to retain/derive/remove any internal stance is documented with executable evidence.
