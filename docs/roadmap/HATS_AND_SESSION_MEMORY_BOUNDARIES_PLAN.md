# Hats and session memory boundaries

**Status:** Active
**Topic:** [Bear memory and hats](../topics/bear-memory-hats.md).

Implementation started: a Bear-owned hat schema, typed hat ID, internal create/list/allow-surface functions, and guarded canonical conversation/Job binding and current-eligibility lookup have database tests. Per-Bear SQLite can now store distinct source-local and hat-scoped records and migrate old profile-local rows without promoting them; storage tests cover new and upgraded databases. Bear-admin routes now create and configure hats, start an owner-scoped hat-bound chat, bind an empty inactive conversation once, and bind an eligible draft Job once; bound turns already use hat bindings for memory. Enabling Work requires a permitted surface: an empty hat passes directly, while a populated hat requires a complete Bear-admin review of its historical memory with an auditable snapshot receipt. Populated hats are reviewed 100 records per page: canonical SQLite scans all history in bounded batches to recompute a shared full-snapshot fingerprint, and the final page requires an explicit acknowledgement. Review covers hats of any size; inconsistent snapshots fail closed. New opt-in scoped SQLite read/browse/keyword functions filter on canonical columns and apply the existing access-bearing entity rules; denial tests include a path collision with legacy records and a confined note. The legacy model-facing direct read now enforces its advertised profile/core wall on each record, fixing guessed cross-profile paths; the admin read remains separate. A Den-owned resolver now distinguishes legacy sessions from bound canonical conversations/Work runs and refuses to downgrade a Work run after hat eligibility is revoked. A vector filter expresses the same source/hat/core restriction. Reviewed hat heads now enter the derived index with a canonical typed hat ID, while raw source-local and access-bearing notes remain unindexed; review writes enqueue reconcile when configured. Once any hat exists, whole-Bear reconcile and its watermark omit legacy profile-local heads; creating the first hat best-effort enqueues cleanup of their old points. No-hat Bears retain the legacy profile recall policy. Member semantic search admits only Bear-owned hats and `core/`, and rebuilds every result from current authorized SQLite records. Bound conversations and eligible Work runs now route model-facing memory writes/reads/browse/keyword search using the canonical grant, with a Postgres-backed two-conversation test of persistence and next-tool access. Bound turn-start projection replaces legacy profile highlights with source/hat highlights and scoped recall; derived hits are rechecked against SQLite before rendering, including stale archive and path-collision cases. Bears without hats still use legacy profile-local memory; on a configured Bear, unbound human conversations are denied before an ordinary turn and unbound Work runs are denied at checkout and before sandbox provisioning (as well as turn start), while owner-authorized historical transcripts remain readable. Raw source-local notes remain unindexed and member semantic search degrades to curated keyword when recall is unavailable; opted-in Curate publication to the source conversation's hat applies to all authorized wearers, including eligible Job runs. The approved Den-tool continuation path preserves its Work-run ID. Bound prompt-memory selection and list/upsert/patch tools now admit Bear-wide reads and exact-client-session blocks only, with mutations limited to the current session. Postgres upserts cannot reassign a block ID to another Bear or scope, and patches are Bear/profile constrained. Scoped `memory_status` and `session_info` avoid exposing legacy profile counts or labels; bound turns ignore opaque supplied runtime context in favor of Den compilation. This is a *human-turn cutover*, not completion of Bear-wide session isolation: historical unbound memory and internal non-human paths need review, alongside retrospective memory import, historical ownerless conversations, and ambiguous client-session IDs still need explicit policy before a complete hat rollout. The ordinary member memory library now admits only canonical shared and Bear-owned hat records, with direct-ID/history enforcement and access-bearing checks; raw entity and reflection/proposal inspection is admin-only. Member semantic search now canonically rechecks derived candidate IDs and reconstructs safe snippets before display; unavailable/stale recall still falls back to curated keyword. The browser chat now exposes a separate owner-verified, source-only read of current private conversation notes (up to 50) without widening the shared memory library or admin transcript reads. The memory dashboard previews eight of the signed-in person's unrestricted current notes across their 200 most recently updated active, hat-bound conversations; Bear admins do not inherit another person's notes in this panel. This plan tests a simpler Bear mental model rather than committing to a hat-first platform migration. The [topic](../topics/bear-memory-hats.md) distinguishes current behavior from the target. A hat is a configured responsibility and resource/capability *limit*; it is neither another Bear nor a replacement for a Job, Mission, work surface, Connection, or governance state. Canonical cognition remains in per-Bear SQLite. Transcripts, Docket state, prompt-memory blocks, and derived recall are distinct state owners. Do not add another writable copy of hat permissions or memory.

## Gate 0 — Verify the contract before widening runtime behavior

- Define typed authorization inputs without assuming a stance label: authenticated human/membership; immutable conversation/Job source and hat binding; actual trusted armature or channel origin; effective resource grants; approved Job/run context; Den supervision and approval state. The hat owns positive tool and network grants, but those grants never override Den safety rules, human membership, an armature's actual availability, Connection credentials, Job/run authority, or work-surface ceilings. Model text, prompts, tool results, and UI labels never grant authority. A client reconnection cannot change the durable conversation binding; a hat or work-surface change requires an explicit rebind with reevaluation. Work runs derive their hat from the assigned Job; a run may retain an immutable authorization snapshot for audit but may not keep a second writable grant.
- Define the ordinary memory read set as own source-unit uncurated records + authorized hat-curated records + Bear `core/`. No ordinary path to another session's raw memory. Only the privileged curation/review path may inspect source records across sessions, and it has no arbitrary outbound execution path. No cross-session raw access via semantic search, keyword search, direct memory read/browse, graph expansion, turn-start projection, prompt-memory blocks, exports exposed to the model, or legacy aliases.
- Do not assume `client_session_id` is a durable memory bucket: the state inventory identifies canonical conversation as the durable interactive container, distinct from client sessions. Confirm the stable Work-run and intake source IDs before writing migrations. Decide whether hat membership is Bear-wide or person-private before public rollout; the isolated prototype can use a clearly shared Bear-owned hat.
- Challenge whether a closed execution class is needed for curation, ingress, and outbound work. Do not remove `TrustProfile` first and later recreate the same boundary as ad hoc string flags. Update the state-machine inventory and the affected ADRs when a concrete authority design is accepted; this draft is not that decision.

**Proposed policy matrix to review** (describes the target, not current enforcement):

| Verified source | Ordinary memory available | Effects and hard denial |
| --- | --- | --- |
| Human conversation over a channel | Own conversation notes, hat-curated, Bear core | Den-hosted tools under channel policy; no armature-local tools without a verified armature. |
| Same conversation through a verified armature | Same notes as above | Local tools only through armature obligations/approvals; changing client connection does not change which conversation's notes are owned. |
| Interactive run after armature disconnect | Same memory owner, subject to current user/policy authorization | Governance may change; absent client cannot supply local tools or approvals. |
| Job-authorized background run | Own Work-run notes, approved hat-curated, Bear core | Only Job-scoped tools, resources, and egress; never raw notes from the originating conversation. |
| Authenticated inbound event intake | Only its own payload/source unit and authorized curated context | Can record an observation, never initiate outbound effects from the event itself. |
| Privileged curation process | Reviewable raw source notes and curated records needed for review | May promote with provenance; no arbitrary outbound execution. Not a general-purpose ordinary session. |

All ordinary rows deny other source units' uncurated memory regardless of common hat, historical profile, tool implementation, or knowledge of a record ID. This matrix deliberately does not grant permissions merely because an origin is named: Den must authenticate the source, check the hat, and enforce resource/action limits at execution. Review who may access raw notes through other human management endpoints and exports separately. The member-facing memory library now filters raw notes, but Bear admins deliberately retain an explicit broad inspection path.

**Exit:** one reviewed matrix of allowed/denied memory reads and tool/action classes for interactive channel, verified armature, disconnected continuation, approved Work run, inbound intake, and curator. A table-driven executable policy test belongs beside the authoritative typed resolver once it exists, not as a prompt-only assertion.

## Gate 0A — Hat-owned tool and network permissions (partial cutover; exit pending)

**Decision:** Den owns one canonical access policy per Bear-owned hat. Its positive grants name descriptor-owned tool/action classes and normalized network destinations. A grant is intended for authorized conversations and eligible Job runs wearing that hat, including later unattended runs once each effect path enforces the resolver; no stance, prompt, model output, client cache, work surface, or Connection can create a hat grant. Bear membership, actor/Connection credential scope, verified channel or armature origin, live Job/run, current work-surface bounds, platform/SSRF denials, and approvals can only narrow it. Internal Curate/Watch execution gets narrow Den-owned system authority, never an implicit IDE/default hat. No duplicate writable permission copies in Den, an armature, or a gateway.

| Interactive decision | Durable effect | UX and authority |
| --- | --- | --- |
| **Just this time** | No reusable grant. The exact `(run_id, tool_call_id or approval_id)` obligation and consumption audit may be durable; replay, a later fetch or tool call, another hat, or a different destination needs its own decision. | Offer for an approvable action to its authorized human. Den consumes it once; it must not be implemented as a time-limited Bear-wide approval. |
| **Always for [hat name]** | Den-owned grant keyed by canonical `(bear_id, hat_id)` plus descriptor action class and the narrow applicable target (managed surface/workspace root and directory, command or safe command family, exact host or known-site account). An action-wide grant, if offered at all, remains within that hat and hard resource bounds. | Explicitly say it also affects future conversations and eligible Jobs wearing the hat. Only a Bear admin or delegated hat-policy manager may make this shared change; other members may request it, not silently commit it. Renaming a hat keeps the grant by ID; disabling/removing the hat or revoking a grant takes effect on the next request. |

An enabled hat alone neither starts a run nor supplies a tool, network route, workspace, or credential. A host grant permits a named destination, not authentication; redirect/DNS/private-address restrictions still apply. Den-hosted web fetch/search/browser paths and sandbox gateway egress must consult the same canonical hat policy at execution, including after reconnect or governance changes. The work surface's host list and workspace path bounds remain environment-specific **ceilings** to intersect with the hat's positive grant; a surface entry is not another independently authorizing audience. Client-local filesystem/terminal/MCP tools additionally require a verified connected armature and its own sandbox/OS permission. Per-hat permanent grants must not be replayable through a different human's credential or a Job outside its assigned surfaces.

**Implementation order:**

1. **Close the once gap first.** Den-hosted `web_fetch` now binds its approved native tool call to one server-generated continuation request and atomically consumes the approval for the exact URL. `allow_once` does not persist a Bear-wide web grant; redirected URLs are not followed, DNS is resolved once and pinned to vetted public addresses without an ambient proxy, and a timestamped migration revokes historical expiring ACP URL grants. Focused tests cover wrong Bear/session/request/URL and replay without external HTTP. The armature now labels the one-time choice `Just this time`; URL-targeted client-local actions offer no persistent choice, do not save or reuse URL host/account/global cached approvals, and reject stale host/account selections. The separate Den-owned `web_fetch` ACP flow can now offer an admin's persistent exact-host choice for the verified current hat; it never writes the client cache. BearWire rejects permanent host/site-account `web_fetch` approvals instead of creating Bear-wide rows, including when an older client still offers those choices. Client-local remembered approvals are now offered/reused only for Den-verified no-hat Bears: every local permission checks the authenticated session's hat directory, and a configured or unverifiable Bear clears its Bear/client cache and uses one-shot prompts. This prevents historic local approvals from crossing hats. A narrow Den-owned ACP `Always for [hat]` option now exists for an eligible read-only filesystem action in the exact editor root; other local-tool families still need scoped persistent choices. Audit the remaining action families for one-time reuse and require equivalent obligation tests before broad hat grants are enabled.
2. **Canonical typed hat policy.** Den now stores Bear/hat-scoped tool-action and exact HTTPS-host grant records. Provider aliases resolve to canonical descriptor actions; admin writes and revocations are Bear/hat-checked in SQL, and conversation reads require current membership, source ownership, and binding. A narrow HTTPS fetch check also requires both the canonical web-fetch tool grant and exact host grant; it is not yet an effect authorization because descriptor, actor credential, armature, surface, and platform checks remain separate. For a separately eligible Job, the Work dispatcher now uses that intersection to set a typed per-run ceiling before task start and token mint; Den refuses an old or unreachable provider before task start or token mint, and the upgraded provider intersects the ceiling again against its current root at provisioning and rejects an open network with a ceiling. Restricted-network relays pin a vetted public IPv4 per allowed host at provisioning, rejecting mixed public/private DNS, IPv6-only answers, and DNS lookups exceeding ten seconds instead of letting `socat` re-resolve the host on reconnect. Hat-bound external relays now additionally require Den's live decision on each new TCP connection; no-hat relays retain the legacy pinned-host route. Den now records each provisioned hat-run ceiling and rechecks it against the current eligible Job, hat, and surface at worker polls; a narrowed or unverifiable policy cancels the run and retries provider teardown rather than marking a failed cleanup terminal. Den now exposes a BearWire `work.egress.check` for an exact HTTPS host: it requires the run-minted token ID, a live uncancelled sandbox run owned by that token's human and still selected as its Job's current non-revoked run, a provisioned host snapshot, and current hat/surface grants. Its tests deny foreign token IDs, actors, Bears, unprovisioned hosts, and revoked hosts. The upgraded provider now runs a Den-checking relay script from an upgraded sandbox image, passes the run token in a private env file rather than Docker arguments, and refuses old images missing the guarded entrypoint. Pre-gateway hat-run snapshots now fail the worker's policy recheck and request cancellation on the next owned poll; they cannot be presented to the new Den egress decision as authorized. Den outage/rejection closes new connections before dialing the pinned host. Already-open streams can continue for at most 60 seconds, so this is per-connection, not per-HTTP-request or instantaneous revocation. The optional provider service is not running locally; script tests cover mocked Den allow/deny/unreachable, the base and provider images built and an unprivileged base-image listener started, but a real sandbox Job and provider relay under revocation remain unverified. Provider-owned git upstream and credential operations remain separate. The hosted Cargo dependency-preparation helper still uses an unrestricted Docker bridge; Den rejects it for hat-bound Work and omits it from new bound Work model rosters. The provider now also refuses automatic Cargo fetch during hat-bound Rust workspace provisioning, before starting that unrestricted helper. No-hat legacy Work retains its helper; a grant-enforced dependency cache is required before hat-bound Rust Jobs can provision. Den-hosted `web_fetch` now uses these records as its configured-hat fetch gate: current member/creator, bound hat, descriptor tool grant, exact HTTPS-host grant, and Bear block policy are checked on each attempt. Bear-wide preferred/allowed sources and approvals no longer authorize a fetch under a configured hat. Creating the first hat now revokes any active Bear-wide web approvals in the same Bear-row-locked transaction; the migration revokes earlier active rows on configured Bears, and the locked legacy writer refuses further Bear-wide approvals while hats exist. The resources UI hides those approval and `allowed`-source controls on configured Bears while retaining preferred-source search hints and explicit Bear blocks. Exact one-shot URL/continuation approvals remain a separate bounded interactive alternative. The fetch audit now admits `hat_host` and `approved_once`, fixing its missing one-shot database kind. The Bear-admin Hats page now provides a narrowly scoped editor for the `web_fetch` tool grant and exact HTTPS hosts: add requires an explicit future-Job-audience acknowledgement and revoke takes effect at the next fetch decision. Other modes and tools do not inherit this exemption. Configured-hat `web_search` now requires the current conversation owner and both its descriptor tool grant and the exact Brave provider-host grant before sending a query; an explicit Bear web block still wins.
