The file-inspection follow-on links each readable attachment name to a content-first screen with **Details** for audience, owner, creator and record identity. The code-only shared-file follow-on makes the existing **Share with this Bear** choice usable for text/JSON: `cabinet_read` discovers only readable current-page attachments and serves bounded character slices under independent page/file/source checks. Validation uses injected storage/isolated data; no server deployment or configuration change is part of this slice.

The model-configuration follow-on adds named Bear configurations, a Bear default selector and optional hat references, with actual ordinary-turn reasoning request plumbing. Model availability and unsupported reasoning remain visible, references prevent deletion, and version-3 bundles remint configuration IDs and hat/default references after destination-catalog validation. The **full target is still not complete**: executable/tool-bearing Skills and model-authored proposal tools, non-repository provider adapters, combined Job approval aggregation, Cabinet recall and general artifact/orphan lifecycle management, pre-export curation flushing, and a universal scoped memory record editor remain separate work. Existing memory review/removal workflows remain available. Current browser bundles include private/source-local memory but never live credentials or grants; imported entities/handles require fresh resolution. Browser Chat retains its existing JavaScript client; management forms and navigation are server-rendered.

## The promise on screen

A person should be able to **see, understand, and change** what their Bear is, knows, can reach, and has done. The UI is a working control surface, not a read-only dashboard wrapped around chat. It should feel obvious to a non-technical person without paragraphs of in-page instruction: familiar labels, concrete state, a next action, and a natural path to open the covers.

The Bear has a single visible navigation list, softly grouped under **Yours** and **This Den**. Yours contains Purpose, Hats, Memory and Skills; This Den contains Tools, Connections, What it can use, Jobs, Cabinet, Activity and People. Overview, Chat and Backup & move remain outside those groups. The Den header gives direct access to Bears, the one shared Cabinet, reusable Connections and Reviews. Bear links to Cabinet and Connections open those **same** Den-wide web destinations, not copies. See the [navigation model](bear-management-model.md#navigation-and-destinations) for the exact map.

The shared shell keeps a **persistent left navigation rail** on normal authenticated application pages, including the repaired operator console:  Bear destinations while managing a Bear, Den destinations on Cabinet, Connections, Reviews and other shared screens. The rail stays left on narrow viewports, is sticky during page scrolling and scrolls independently when its links exceed viewport height. Content boxes fill the available column, with a small clear gap beyond their offset shadows. Shared screens do not invent or retain a hidden selected Bear.

The labels themselves do most of the explaining. “Jobs” is work to direct; “Activity” is a record to inspect. “Memory” is what the Bear knows; “Cabinet” is shared pages that humans and authorized Bears edit together. “What it can use” shows concrete repositories, documents, designs and servers rather than asking people to learn “work surfaces” or “resources.” The grouping suggests what can travel with the Bear; a short what-moves preview provides precision when it matters.

## Design rules

1. **Show state before exposition.** Every area leads with a name, status, provenance and available action. Explanations belong in optional details, not as a substitute for discoverable navigation. Overview exposes links to knowledge, reach, work and history at every screen size.
2. **Inspection leads to control.** A readable memory has a correction or review route; a grant has a revoke route; a Job has its authorized work controls; a shared page has edit/history/access controls. Where a user lacks authority, show the state without implying they can change it.
3. **Make authority visible, not magical.** Show what a hat is used for, what access it restricts, where a tool runs and which Connection enables it. A hat or skill cannot confer a credential, tool or approval. Flag risky configurations as questions to review, never as a “safe” guarantee.
4. **Keep ownership honest.** Bear identity, reviewed knowledge and owned procedures are distinct from host credentials, conversations, Docket work, Cabinet pages and membership. Preview actual export contents; never smuggle secrets or transcripts into a Bear package or present a remembered link as if it exported the linked thing.
5. **Trace cause and effect with permissions.** Link a permitted conversation to its Jobs and reviewed memories, a Job to runs/evidence and its Cabinet page, and a memory to a readable source. Hide unauthorized records and source details, not just their edit buttons.
6. **No irreversible surprises.** Preview the affected audience and active work before widening access or enabling Work; explain the effect of forget, revoke, archive and delete before confirming. Show an actionable conflict when a version changed while someone was editing.

## Screen contract

All destinations and actions below are **target** behavior. They should work as Den web pages; a link may change Den scope but never require a CLI, editor or separate Cabinet app. Show only authorized data in summaries as well as detail views.

### Entry, Purpose, Hats and Chat

- **Bears / setup:** Create or select a Bear in the Den header. Ask for a name, charter and usable model with conservative starting access; show the initial effective reach before any real-world action. The charter is a property of the Bear, not a separately managed object.
- **Overview:** Compact at every size: Bear identity, health, direct Chat action, current responsibilities, active permitted Jobs, a permission-filtered review count and recent visible activity. “Memory,” “What it can use,” and “Jobs” are direct links to inspect the Bear. On larger screens add model/context usage and trends only if backed by real data and accessible to this viewer; the small-screen core is complete.
- **Purpose:** Edit name, slug and charter; open **Models** to create/edit/delete named configurations, choose a Bear default or inherit the deployment default. Each configuration has a model and Reasoning effort (Model default/Low/Medium/High). Lead with the effective name/model/effort/source and availability, not provider documentation. Keep loop-control/budget and gateway governance separate. Preview the effective Bear-wide identity and indicate the next-turn boundary. Do not frame a model change as upgrading the Bear's mind.
- **Hats:** Create, rename and edit a named responsibility, its authored identity and allowed subset of already Bear-granted things. Show which hat a chat or Job uses, the IDE default, and whether Work is off or eligible. **Primary model** inherits the Bear configuration or references a named override; display the inherited/effective model and effort. Configurations do not grant helper execution or change hat identity. Enabling Work is an **admin-reviewed audience change**: show hat identity and the entire required historical hat-memory snapshot, request the right acknowledgement/rationale, and refuse stale or incomplete review. Even after enablement, a Job and current policy must authorize execution. Never present hat prose as a permission grant.
- **Chat:** Start a conversation with a chosen hat when required, and resume only authorized threads. Keep the transcript, own source-local notes, Docket task-list projection, linked Jobs and reviewable memory distinct. An unbound historical thread that cannot run remains visibly read-only, not silently rebound. Web chat does not inherit editor-local tools. Its model selector labels explicit choices as pins and automatic selection as inheritance. A pin replaces the entire configuration, including reasoning; clearing it restores the current hat/Bear default. Unavailable selections must not show a stale effective model.

### Yours: Memory and Skills

- **Memory:** Browse and search by understandable scope: Bear-wide, reviewed hat knowledge, and (in its owner's conversation) own notes. A record opens content, author/audience, dates, source and promotion lineage, history, and the permitted **correct**, **forget** or **request review** action. Correct by superseding the canonical record; forgetting must stop it being used, not just hide a row. Keep derived recall visibly distinct from canonical records, and do not claim semantic results are permission-safe until they are checked against canonical scope. Private conversation/Work notes never become shared merely because they use the same hat. Admin-only evidence/entity detail remains admin-only until a safe member projection exists.
- **Skills:** List owned procedures with source, trust, applicable uses and review state. A Bear-authored or tool-bearing proposal waits for the appropriate review before being made effective. Attach/edit/remove where authorized; show if a skill supplies tools as well as instructing their use. Owning a procedure does not bypass Tools or access policy.

### This Den: live reach and work

- **Tools:** One origin-tagged catalog (Den-hosted, armature-local, remote/MCP). Show which tool is available in which verified context, what it can expose, its enabling Connection where applicable, and controls to grant/revoke or request approval. Local editor tools are not offered in browser chat just because they appear in the Bear's inventory.
- **Connections:** Show reusable external accounts, provider, owner, named secret status and affected Bears. Set up/revoke at the single Den-wide destination; the Bear view shows only its attachments and links to the shared record. Never render secret values. Losing a connection or grant must invalidate affected reach, not just change a badge.
- **What it can use:** Typed cards for repositories, documents, designs and servers; show web policy and internal Cabinet reach separately. Each card says what is readable/writable, which Connection/policy enables it and what each hat/use can actually access. Grant/revoke in the web UI; explain the combined data-read/outbound/untrusted-input risk where relevant. A link to Cabinet access does not duplicate Cabinet page membership.
- **Jobs (Docket):** Bear-filtered queue with create/edit, task tree, criteria, priority and assignment/hat; dispatch, pause/cancel or resolve when authorized. Open run status, approvals, evidence, output and settlement history. Link an optional Cabinet Mission page as supporting shared knowledge, not as a Job container. Conversation task lists project Docket rather than storing another independently editable work plan. Include recurring work or schedules under Jobs when those controls become available, with their own authority and run history.
- **Cabinet:** Open the **one Den-wide shared page tree**: browse/search, create/edit a page, inspect immutable versions and sources, and archive/restore or person-delete when permitted. A Mission is a page with child pages, not a separate collection. Expose move/reorder, effective inherited page access, membership, conditional Bear-write review and artifact attachments at that page. The local implementation supports those controls and bounded private-by-default uploads with configured storage; safe attachment inspection/previews are available; recall and native-rendering validation remain pending. Job-linked private copies must have a readable evidence/download path, not only a capture button. Human edits publish directly; configured policy can require review of Bear-written changes. Cabinet content is not Bear memory.
- **Activity:** Permission-filtered conversations, Job/run events and Cabinet edits, each linking to its canonical detail and provenance. This is an inspection projection, not a separate event store or a place to edit a Job/page. Keep admin-only diagnostics out of member activity and Overview.
- **People:** Add/remove Bear members and manage Bear roles when authorized. Show effective access before changes; Cabinet page membership/policy belongs to Cabinet, not to the Bear's People screen.

### Across the boundary: Reviews and Backup & move

- **Reviews:** The Den header and Overview offer a permission-filtered inbox with memory/skill proposals, hat Work enablement, Job approvals and (where page policy supports it) pending Cabinet versions. Each item opens its owning record to decide it. Routine curation or Cabinet direct edit is not made approval-gated solely to populate an inbox.
- **Backup & move:** Show what the chosen export actually includes and excludes before download; provide export/import in the browser with version checks, reviewed recent-knowledge curation, model remapping and a re-attach checklist for host credentials, resource grants and membership. A cognition package is not a Den backup: conversations, Docket state, Cabinet pages, raw secrets and derived indexes do not come along. Do not promise a curation flush or package tier unless the backing implementation exists; use honest unavailable states until then.

## Usability implementation checkpoint — code/test only

The four batches from the review below are implemented in this branch, **not deployed**. Routine architecture/tutorial prose is behind scoped Help; records and diagnostics remain inspectable through Details/History; current state, primary actions, genuine failures and privacy/audience/destructive consequences stay visible. Overview, Purpose, Models, Hats, Skills, People, Memory, setup/account, shared pages, repositories and operator screens have the corresponding disclosure/feedback changes. The operator parent now renders the common assets/theme/viewport and one authorized rail, with child title/head blocks intact.

Functional fixes include masked, non-echoing password fields and actionable success/failure feedback; role-aware editor navigation; preserved review/Work-pagination drafts with fresh consent; canonical disabled-Skills status without execution; transactional last-Admin protection for membership demotion/revocation; truthful repository/account and all-assignment Job eligibility projections; no silent replacement of unavailable selections; supported browser publication choices; early Job/run results and recovery; visible Cabinet audience/retention/removal consequences and a current → proposed move preview. OAuth issuance feedback is server-side, expiring and operator/session-bound, with no secrets in redirect queries; shared errors omit private causes.

Chat uses a searchable authorized task picker and explicit canonical confirmation, with stale-conversation responses discarded. Bear import is **upload → review → confirm/cancel**, with no Bear created at upload. Private staging is bounded, owner/session/nonce-bound, expires after 15 minutes, verifies immutable hashes and claims once. Processing is semaphore-bounded; full-slot periodic/startup cleanup respects active guards. Creation reports rollback/retained/uncertain outcomes without deleting a surviving Bear's memory. Preview shows identity/prompts/models/procedures/knowledge audience, **not full SQLite contents**; users must review imported memory before granting members or enabling Work/sharing. No curation flush, helper execution, alternative publication runtime or restore-of-authority was introduced.

Evidence: 299 web tests, 35 Chat JavaScript tests, the focused membership/revocation-race and shared-error suites, strict workspace all-target Clippy, locked production checking, additive SQLx cache preparation and the separate `bears-den-usability-validation:local` production/musl image. Tests render checked-in parent shells, cover failures/conflicts/private metadata, verify persistence and next-turn projection, and exercise review nonce/expiry/tamper/replay/concurrency/cleanup. `sha2` was already locked/present; only its direct use by `den-web` was added, with no new package or feature expansion. No schema migration, `.env`/Compose change, serving-image replacement, commit or push is included. A real authenticated browser/participant walkthrough and live backend/provider acceptance remain outstanding.

**External input still required:** no terms-of-service document/URL exists in the repository. Registration preserves consent and explicitly directs the person to the Den administrator for the terms; no legal policy or fake link was invented.

## Usability review — 2026-10-07

**Historical pre-change findings:** the implementation checkpoint above resolves the code changes described below; the findings are retained as rationale, not claims about the current templates.

**Basis:** source review of active screen families on branch `test` at `c1440157a`, including templates and relevant handlers/service contracts. This is an audit and recommended change order, **not an implementation or deployed-state claim**. It includes public/auth/account/setup, Bear management and Chat, memory/inspection, shared Connections/Reviews, repositories, Docket, Cabinet, and the operator console. Superseded unmounted `admin/bears/*` detail copies were not treated as current screens. No live authenticated browser walkthrough or participant usability test was performed.

### Overall assessment

The ownership-led destinations are useful. Overview, Purpose, Cabinet content/attachment inspection, and several review screens already use disclosure well. The main weakness is **information priority**: routine explanations and implementation detail are often visible before a decision or result, while some actual failures, prerequisites and repair actions are hidden or missing. Fix both directions; wrapping every paragraph in `details` would make this worse.

The desired first view is **object/name → current state → next useful action → relevant content**. Inspection should remain easy, without requiring a person to read architecture documentation to operate the UI.

### Copy and disclosure policy

| Information | Placement | Examples |
|-------------|-----------|----------|
| Current state, primary action and essential content | Visible by default | Effective model/source, current grants, task status/result, Cabinet document, memory entry, readable attachment, review decision. |
| A non-obvious input rule or immediate consequence | A short hint beside that control | Model pin takes precedence; exact host only; file-size limit; replacing a connection clears local credentials. Do not deliberately make people trigger an error to learn these. |
| Audience, confidentiality, destructive effects and informed consent | Visible at the relevant action/confirmation | Automatic sharing/provider disclosure, Work audience change, private export, direct-default-branch work, deletion, retained-copy lifetime and credential revocation. Preserve acknowledgements. |
| General explanation or implementation mechanics | Closed **Help** disclosure near the relevant section | How inheritance works; how access is enforced; context assembly; PKCE background; worker/lease mechanics. Use a specific summary, not one enormous page-wide FAQ. |
| Record metadata, provenance, versions and technical evidence | **More information**, **Details**, **History** or a dedicated inspection destination | Hashes/IDs, lineage, stored snapshots, request attribution, raw logs. Keep a compact provenance/state summary and an obvious path to inspect the full object. |
| A failure, conflict or unavailable prerequisite | Visible when it actually applies; technical evidence optionally expandable | What failed, what was saved/applied, what to do next, preserved draft, retry/referral reference. Do not hide the only explanation or recovery action. |
| Less frequently used but legitimate configuration | **Advanced settings**, not Help | Loop budgets and gateway configuration. Show effective state and access/repair paths outside the disclosure. |
| Duplicate, obsolete, speculative or developer-only prose | Remove or correct, not merely hide | Starter-project copy, retired protected-role claims, TODO/MVP text, unavailable-feature announcements contradicted by code, repeated headings. |

Use native keyboard-accessible disclosures that work without JavaScript. Do not rely on hover tooltips for anything required to complete an action. Keep errors outside closed disclosures, announce new feedback appropriately, and preserve entered values. Avoid explaining a poor label: fix the label instead.

### Priority 1: correctness and feedback before copy polish

1. **Restore the admin shell.** [The parent](../../services/den/crates/den-web/src/templates/admin/base.html), lines 1–9, is only a Runtime link list and `admin_content` block; it does not extend the shared base. Active children such as [Models](../../services/den/crates/den-web/src/templates/admin/models/index.html) therefore lack shared assets, viewport metadata, navigation and shell headings in the default checked-in render path. Their `head` blocks are also not inserted, including sandbox-operation refresh. [Rendering](../../services/den/crates/den-web/src/lib.rs) returns the rendered child directly, with no outer document wrapper. Fix this before declaring the rail universal or polishing operator pages. An externally supplied/build-time template directory could differ; deployment was not inspected.
2. **Repair password-change fields and feedback.** [Password change](../../services/den/crates/den-web/src/templates/account/password.html), lines 10–11, passes an attribute string as the `type` argument and the form as `extra_attrs`, contrary to [the shared input macro](../../services/den/crates/den-web/src/templates/forms.jinja), lines 2–7. This is a source-level defect in masking/constraints, not a need for Help. [The handler](../../services/den/crates/den-web/src/user/account/mod.rs), lines 419–429, also supplies `form.error` rather than the macro's `errors` map. Verify rendered password types/attributes and make validation failures and success explicit without echoing secrets.
3. **Expose action feedback that is hidden or dropped.** [Memory](../../services/den/crates/den-web/src/templates/bear/memory/dashboard.html), lines 7–21, puts import/review notices and errors inside closed diagnostics. [Name editing](../../services/den/crates/den-web/src/templates/bear/edit_overview.html) and [steering editing](../../services/den/crates/den-web/src/templates/bear/edit_prompt.html) check `runtime_sync_error`, while [their handler](../../services/den/crates/den-web/src/bear/management.rs), lines 1058–1078 and 1179–1195, supplies `provision_error` after saved-but-not-initialized failures. [Admin membership](../../services/den/crates/den-web/src/templates/admin/membership/grant.html) omits its supplied validation errors/selections. Show saved-versus-applied state, preserve drafts, and provide a supported recovery route.
4. **Reconcile offered Job output choices with dispatch.** [New Job](../../services/den/crates/den-web/src/templates/work/new.html), lines 68–76, offers `per_job` and `none`; browser dispatch requests repository changes, while [preflight](../../services/den/crates/den-docket/src/dispatch_preflight.rs), lines 55–68, supplies a sandbox publication route only for `per_task`. Unavailable choices need a truthful local state, not a later surprise. The introduction should say creation defines work, not that it starts autonomous execution.
5. **Show canonical connection state.** [Repository detail](../../services/den/crates/den-web/src/templates/work/surface.html), lines 62–108, describes missing local credentials and offers local edits when a reusable account may own authentication. [Account attachment](../../services/den/crates/den-service/src/connections.rs) clears those local fields, and the service rejects incompatible edits. Project the linked account and its management route. Also fix [the Jobs table](../../services/den/crates/den-web/src/templates/work/index.html), line 27: its repository field differs from [the supplied projection](../../services/den/crates/den-web/src/work/mod.rs), lines 675–689, and lifecycle state is currently copied from Job status.
6. **Replace opaque blockers with a next action.** [Hat Work enablement](../../services/den/crates/den-web/src/templates/bear/manage/hat.jinja), lines 165–172, disables enablement for zero resources without a nearby reason/link. [Blocked task details](../../services/den/crates/den-web/src/templates/work/job.html), lines 205–212, hide the reason and Retry inside generic Details. Show the applicable blocker and recovery route immediately; supporting history remains optional.
7. **Replace identifier entry with object selection.** [Chat](../../services/den/crates/den-web/src/templates/bear_chat.html), line 138, asks for a “Task UUID”. Use an authorized task picker with readable titles/status and the existing selection confirmation. A tutorial cannot make guessing/copying internal IDs a legible primary workflow.
8. **Make import consent reviewable.** [Backup & move](../../services/den/crates/den-web/src/templates/bear/manage/portability.html), line 20, and dashboard import require an “I reviewed…” attestation but offer no bundle preview. Add a separate review-before-import step for identity, knowledge audience, destination-model compatibility and disabled authority. Retain consent and new-Bear semantics; do not remove the acknowledgement to shorten the form. This is a flow change, not a copy-only patch.

### Recommended implementation batches

1. **Restore usability and truthful feedback:** admin shell, password fields/validation, dropped/hidden errors, accurate Job output choices/projections, reusable-connection state and actionable prerequisites. Add full-parent rendering regressions, not only fragment/unit stubs.
2. **Copy and disclosure pass:** Hats, Models, setup, memory explanations, PKCE and routine provider/log details. Remove TODO/MVP/retired/stale and duplicate prose. Preserve all safety/audience acknowledgements and current errors.
3. **State/action hierarchy:** Job/run/readiness ordering; visible Skills uses and prefilled editing; post-import repair links; attention-worthy Overview state; scoped Reviews empty state.
4. **Flow changes:** readable Chat task picker and review-before-import. Treat these as functional work with explicit authorization, draft preservation and confirmation tests, not wrapping text in Help.

**Acceptance:** a person can identify current state and the next permitted action without reading Help; Help explains how/why, not where a hidden required action lives. Success/failure/blocker feedback appears immediately, including with JavaScript unavailable where the workflow supports it. Consent still states the actual audience/consequence. Inspection remains one obvious disclosure/link away. Check first-time/repeat, member/admin, healthy/empty/unavailable/conflict and narrow/zoomed views; retain the requested left rail while making forms and table controls usable in the remaining width. Participant/live-page validation is still needed.

## End-to-end journeys to validate

Use non-technical participants, without in-page tutorials, on both narrow and wide screens. Completion means the person can find the destination **and** finish the authorized action in the browser:

| Task | Success observation |
|------|---------------------|
| Start and understand a Bear | Create it, reach Chat, then find its charter, active hat, memory and effective access from Overview without guessing what “stance” means. |
| Audit and correct | From an assertion, open an authorized source and memory, correct/forget it, and see the resulting canonical status; another person's raw conversation stays hidden. |
| Configure models | Create a named configuration, set the Bear default, choose a different hat override, inspect effective model/effort and a conversation pin, then clear the pin and see inheritance restored. Unsupported effort is rejected without losing edits; revoked choices stay repairable. |
| Bound reach | Find which account enables a repository and which tool uses it; revoke access and see the affected hat/use and active work. No need to inspect a config file. |
| Review Work | See what will become available to Work when enabling a hat, inspect the required identity and memory, and decline or confirm; changing the reviewed state does not silently authorize a Job. |
| Direct a Job | Create a Job and task criteria, select an eligible hat, dispatch/stop when permitted, and find run evidence and settlement from its Job page. |
| Manage a Mission | Find Cabinet, create/edit a Mission page and children, inspect versions and effective page access, restrict access and follow a linked Job back to Docket. Where later Cabinet phases are unavailable, the UI says so rather than pretending the task is complete. |
| Move without surprise | Before export, correctly predict whether conversations, Cabinet pages, credentials, grants and memories will follow the Bear; import with a clear re-attachment path. |

## Build posture and delivery boundary

Build semantic, responsive HTML first. All basic navigation and authorized forms should work without JavaScript; JavaScript can improve transitions, not supply missing core actions. Reveal extra *breadth* on large screens, but retain health, reviews, Chat, Jobs, Memory and reach on small screens. Depth-on-demand shows provenance or effective policy when opened; it must not bury the only way to inspect or change something.

This design is a **target**. The [memory/hats topic](../topics/bear-memory-hats.md) records current visibility and review boundaries; the [Docket topic](../topics/docket.md) distinguishes implemented work state from remaining UX; the [Cabinet plan](../roadmap/CABINET_IMPLEMENTATION_PLAN.md) identifies Phase 1 versus later hierarchy, policy/review and attachments. Skills, shared Connections and portability need their own backing contracts and authorization before their target controls are called available. Update the maintained topic/plan and this design as each screen becomes real; do not turn intended behavior into a current claim by changing only the label.
